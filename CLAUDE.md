## Proponer una mejora al cerrar cada entrega

**Instrucción permanente del dueño del repo (2026-09-09): al terminar cualquier tarea, proponer
una mejora.** No es un adorno del resumen: es una propuesta concreta, salida de lo que se acaba
de tocar y de lo que las skills instaladas saben mirar —seguridad (`vibesec`,
`insecure-defaults`, `sharp-edges`), revisión (`differential-review`), interfaz
(`frontend-design`), datos (`database-designer`), entrega (`deployment-practical`)—. Va **junto
al resumen de pendientes**, que ya es obligatorio.

Qué la hace útil, y no ruido:

- **Sale del trabajo recién hecho**, no de un catálogo genérico de buenas prácticas. Si se acaba
  de tocar el BOM, la mejora habla del BOM.
- **Dice el porqué y el coste**, no solo el qué: qué problema evita, qué cuesta y qué se rompe si
  se hace mal. Una mejora sin coste declarado es una que nadie puede priorizar.
- **Es una, no una lista.** La mejor. Un listado de cinco se lee como relleno y no se ejecuta
  ninguna.
- **Se puede rechazar sin discusión.** Es una propuesta, no un trabajo empezado: no se implementa
  sola ni se da por aprobada por silencio.
- Si de verdad no hay ninguna que merezca la pena, **se dice eso** en vez de inventar una. Una
  mejora inventada por cumplir el trámite es el mismo vicio que un dato inventado por rellenar
  un campo.

## Overview

Presales is a set of internal network-equipment presales tools — sizing calculators, a BOM/quote generator, and a design guide — for Huawei, Cisco, Fortinet, MikroTik, Aruba, Nokia and Juniper gear. **Arista se retiró por completo** (agosto 2026, decisión del dueño del repo: fabricante que por ahora no interesa) — catálogo del portal, filas del cotizador, entradas de la guía de diseño, la página del portal y su fabricante en la base. It's an Express + SQLite backend serving a set of vanilla HTML/CSS/JS pages behind a shared-credential login, deployed as a single Railway service, mirroring the architecture of the sibling projects `chikisdtv` and `credifuturo`. UI text is in Spanish (`lang="es"`); code identifiers (functions, variables) are in English.

**Idioma: todo el texto visible para el usuario (UI, etiquetas, mensajes, comentarios explicativos) debe escribirse en español**, siguiendo la convención existente. Los identificadores de código (nombres de funciones/variables) se mantienen en inglés. Al conversar sobre este proyecto, responde en español.

## Running / developing

```
npm install
npm run dev        # nodemon server/server.js, http://localhost:4000
npm start           # node server/server.js
```

No build step for the frontend — `public/*.html` and `public/js/*.js` are served as-is by Express's static middleware; edit and reload. `DATABASE_PATH` (see `.env.example`) controls where the SQLite file lives; unset it locally and it defaults to `./database.sqlite`. On first boot with an empty DB, `server/seed/seedCatalog.js` seeds the catalog automatically — delete `database.sqlite` to force a reseed.

Set `AUTH_PASSWORD` in `.env` before starting, or nobody can log in: locally the server only warns, but with `NODE_ENV=production` it refuses to boot rather than serving prices to the open web. The other auth variables (`AUTH_USER`, `SESSION_SECRET`, `AUTH_STATE_DIR`) are documented in `.env.example`.

```
npm run verificar   # lint + pruebas, lo que hay que pasar antes de empujar
npm test            # node --test, sin dependencias
npm run lint        # eslint
npm run catalogo    # inventario: cobertura por campo, ciclo de vida, precios y procedencia
npm run pantallas   # conduce las 16 pantallas en Chromium y captura cada una (ver Deploying)
npm run skus        # referencias de pedido de Fortinet desde la price list (ver Referencias)
npm run lista-aruba # lista de precios del distribuidor (Aruba): dry-run salvo --aplicar
npm run contraste   # contraste antes/despues de un refactor, en Chromium (ver Deploying)
```

**`npm run catalogo` también cruza cada pantalla con su estado.** Los dos fallos del 2026-09-13 fueron de la misma clase y este inventario no miraba nada de la capa de presentación: el refactor de Aruba retiró `#bw` y dejó `pantallas.yml` en rojo cuatro días. La sección «PANTALLAS» cruza los `campos` que cada dimensionador declara en `ESTADO.vincular()` contra los `id=` de su propio HTML; un campo declarado que ya no existe deja de reponerse y el enlace compartido llega mudo. **Se parsea en vez de ejecutarse** porque en `dimensionador-nokia-7220ixr.js` la llamada vive tras un `await fetch(...)`, y una página que no se sepa leer se reporta como **error**, nunca se salta — un comprobador que no comprueba se porta igual que uno que pasa. Los ids que crea un módulo en tiempo de ejecución (`verdict-sel`, que pinta `ficha.js`) se declaran en `TARDIOS` **con el ancla que debe seguir existiendo en ese módulo**, así que la excepción caduca sola si el control desaparece. Esa ancla se aprendió saboteando: la primera versión anclaba en `${cid}-sel` y al renombrar el control a `${cid}-selector` **no saltó**, porque el ancla corta seguía siendo subcadena de la larga. Lo guarda `test/pantallas-campos.test.js`, que es lo que hace que `npm run verificar` lo frene y no solo lo cuente.

**`npm run catalogo` dice qué falta sin salir a internet.** Generaliza a los seis catálogos lo que solo hacían `cps --check` y `juniper --check`: cuántos modelos traen cada campo, cuántos avisos de fin de venta ya vencieron, cuántos equipos van sin precio y de qué fecha es cada fuente. Los precios se cuentan sobre `cotizadorCatalog.js` y no sobre los `MODELS` de cada fabricante — contarlo allí daba «Fortinet 0/58 sin cotizar» justo del único fabricante con lista firmada, y un informe que miente es peor que no tenerlo.

**Las pruebas cubren lo que ya falló, no lo que es fácil de probar.** 181 casos sobre la
identidad y la firma de sesión (la migración que se rehacía en cada lectura e invalidaba la
sesión recién creada), la regla única de fin de venta de `ficha.js`, el trinquete de la selección (que mostraba siempre el mismo equipo), el tercer estado de `redund` (nunca leer `undefined` como `false`), el orden de columnas
(donde 5.999 dólares valían menos que 29), el casado de nombres entre dimensionador y
cotizador, el parser del importador Juniper, la coherencia del catálogo, y la sincronización
que fallaba abierta (permiso `sync` sin exigir, simulacro sin clave, mimetype del navegador), y la
capa que dimensiona cada perfil de la calculadora — que era la de portada en el perfil con inspección.
`test/servidor-produccion.test.js` arranca el servidor real con `NODE_ENV=production` y lo
interroga por HTTP: es la única prueba que cruza todas las capas y la que cazó que `exige`
redirigía la API en vez de responder 403. `test/ayuda/navegador.js`
carga los módulos de `public/js/` en Node con un doble mínimo de `document`: son IIFE sin
sistema de módulos, y traer jsdom para probar funciones puras sería una dependencia grande
para nada.

**El lint no es un manual de estilo: cada regla activada corresponde a un fallo que este
repositorio ya tuvo.** `no-undef` habría cazado el `BOM is not defined` del cotizador,
`no-use-before-define` el TDZ de `capDe` en la página de Cisco, y `no-eval`/`no-new-func`
existen porque la CSP de este sitio los haría fallar solo en producción. No se activa nada de
formato: reformatear produciría un diff enorme sin arreglar nada.

## Deploying

**Standing instruction from the repo owner: work goes to production.** Railway's `presales-web` service (project `Presales`, environment `production`) auto-deploys from `main`, so finishing a change means merging it to `main` and pushing — don't ask first and don't leave completed work parked on a branch. The permission to push `main` is granted; it is the deploy trigger.

**Desde septiembre de 2026 ese «no preguntes» tiene red.** `.github/workflows/verificar.yml` corre en cada push y cada PR: `npm ci`, lint, las pruebas, y un arranque real con `NODE_ENV=production` que exige ver `[seed]`, la línea de `listen` y un `/salud` que responda `ok`. Railway espera a esas comprobaciones antes de construir, así que un push con las pruebas rotas ya no llega a producción. **Pero esa red tiene dos agujeros medidos, y conviene no confiarle más de lo que aguanta.**

**El segundo se midió el 2026-09-14 y es de otra clase: un push de bot no crea ningún check, así que Railway no espera a nada.** El commit `61dedc65` del propio vigía se desplegó con SUCCESS **sin que existiera ni una corrida de `verificar` ni de `pantallas`** para ese SHA — GitHub no dispara workflows para eventos originados con el `GITHUB_TOKEN` por defecto, para evitar bucles recursivos. Un *required check* tampoco lo cerraría por sí solo: un push que no crea ningún check no puede fallarlo. Se arregló haciendo que el vigía **abra un PR** en vez de empujar a `main`, así el camino a producción pasa por una persona en cualquiera de los dos casos posibles (si el PR de bot crea corridas pendientes de aprobación, un mantenedor las aprueba; y si no crea ninguna, el merge lo hace una persona y **ese** push sí dispara CI). Un PAT o un App token harían que el push disparara los workflows, pero meten un secreto de larga vida con escritura sobre `main`: peor, y la misma forma que este repositorio ya rechazó al descartar el staging. De paso deja de redesplegar producción cada semana por un archivo que el servidor no lee.

**El primero: Railway espera a `verificar` y NO a `pantallas`.** El 2026-09-13 el commit `7fe786e` desplegó con SUCCESS teniendo la comprobación de navegador en rojo — la cabecera de `pantallas.yml` afirma «ESTE CHECK FRENA EL DESPLIEGUE» y no es cierto. Una pantalla rota **sí** llega a producción; lo que no llega es una prueba rota. Convertirlo en *required check* es una decisión abierta (`PENDIENTES.md`, punto 33). Antes sí llegaba — y `npm ci` falla cerrado cuando `package.json` y `package-lock.json` no coinciden, que es justo lo que tumbó el despliegue del 1 de septiembre sin que nadie se enterara hasta el día siguiente. Dependabot abre PR semanales de parches y menores, que pasan por el mismo workflow.

What that does *not* license is shipping unverified work. The checks below are exactly what makes an always-deploy default safe rather than reckless, so they stay:

- **Boot with `NODE_ENV=production` before pushing.** Three behaviours exist only in that mode and so are invisible in `npm run dev`: the server refuses to start without `AUTH_PASSWORD` (fail-closed, deliberately), the session cookie gains `Secure`, and both `/api/sync/*` routes return 503.
- **Drive the changed page in a browser, not just the API.** Every real regression this repo has had was invisible to `curl`: a page whose own script sat behind the auth wall, a stale `onclick` surviving inside a JS template, a gateway filtered out by its hardware-only capacity. Chromium is preinstalled at `/opt/pw-browsers/chromium-1194/chrome-linux/chrome`. **Desde el 2026-09-04 eso ya no depende de que alguien se acuerde:** `npm run pantallas` (`scripts/verificar-pantallas.js`) conduce las 16 pantallas detrás del muro —las once secciones del portal, el comparador, las seis capas de la calculadora, los ocho dimensionadores con su pestaña de BOM, un enlace compartido v1 de Aruba que tiene que migrar al builder, el cotizador, la guía, cuenta y usuarios—, falla ante un error de consola, una excepción, una petición fallida **al propio origen** o un contenedor que se queda vacío, y deja una captura de cada una. `.github/workflows/pantallas.yml` lo corre en cada push y sube las capturas como artefacto. Se comprobó que detecta de verdad, no solo que pasa: quitando `public/js/comparador.js` el informe dice «`#compareOut` se quedó vacío» y reproduce la firma histórica exacta —«Refused to execute script… MIME type ('text/html')»—, que es el fallo del script tras el muro de auth. Lo que **no** se comprueba ahí es ninguna cifra del catálogo: para eso están las pruebas, y una aserción sobre «3,1 Gbps» se rompería en cada cambio de catálogo, que es como se enseña a la gente a ignorar un rojo.
- **Confirm the deployment after pushing.** A green build is not a running app: check the Railway deployment reaches SUCCESS *and* that its container logs show the `[seed]` line and the `Presales corriendo en` line. Reaching `listen` is also the proof that `AUTH_PASSWORD` is set, since production throws without it. `/salud` (público, sin sesión, en `server.js`) es la misma comprobación por HTTP: devuelve `{ok, fabricantes, modelos}` y responde **503** si la base está vacía o no responde, porque un `{ok:true}` fijo estaría igual de verde con el catálogo sin sembrar. Railway lo tiene como `healthcheckPath`, así que un contenedor que no llega a servir no sustituye al que funciona.

**`npm run contraste` prueba que un refactor NO cambió lo que decide una pantalla, y desde el 2026-09-16 corre en CI.** Va **dentro del job de `pantallas`** y no en un workflow propio, porque necesita exactamente lo que ese job ya monta: Chromium, un servidor en modo producción y una clave que vive y muere con la corrida; uno aparte pagaría ese montaje dos veces para comprobar lo mismo sobre el mismo commit. **Las dos comprobaciones miran cosas distintas y por eso conviven**: `pantallas` verifica que *nada explota* y **no compara ninguna cifra** —una aserción sobre «3,1 Gbps» se rompería en cada cambio de catálogo—, mientras el contraste compara *la recomendación* para un escenario ya medido. Ni `verificar` (funciones puras) ni `pantallas` cubrían eso. Se ejecuta **aunque las pantallas fallen** —pero no si el servidor no arrancó—, para no necesitar una segunda corrida y enterarse de la otra mitad. **Ojo con lo que esto sí y no gatea:** Railway espera a `verificar` y **no** a `pantallas` (pendiente 33), así que un contraste en rojo **no** frena el despliegue hoy; lo frenará el día que ese pendiente se cierre. `--todos` deriva la lista de `scripts/contrastes/`, así que añadir un caso es añadir un archivo y no tocar el workflow: una lista escrita en el YAML se quedaría atrás y un caso que nunca corre se porta igual que uno que pasa. Cada caso declara `medidoEn: {commit, fecha}` y el informe lo **imprime**, porque una línea base medida hace meses sigue pasando en verde y ya no quiere decir lo mismo — misma regla que la fecha de cada fuente. `test/contraste-casos.test.js` frena en `npm run verificar` lo que se ve leyendo el archivo (un caso sin `leer`, una pantalla renombrada, una clave que la línea base no mide, una procedencia ausente), para no gastar diez minutos de navegador en un fallo de segundos.

**Y la corrida MIDE sobre qué módulos de `public/js/` vale esa prueba, en vez de declararlo.** La primera idea era que cada caso declarara `cubre: ['ficha.js']`, y se descartó por su propio riesgo: un caso que declare cubrir `bom.js` sin conducir una línea del BOM da una cobertura **falsa**, peor que no tener el dato porque invita a no escribir el caso que falta — la forma exacta del `noAplica` deducido y del `estable` puesto a ojo. Chromium no se puede rellenar a mano: `page.coverage` dice qué funciones de cada script se ejecutaron, `scripts/ayuda/cobertura.js` lo agrega y el resultado va a `scripts/contrastes/cobertura.lock.json`, que `npm run catalogo` pinta en la sección «COBERTURA DEL CONTRASTE». **La métrica son funciones ejecutadas y no bytes** porque los rangos de V8 **anidan** y sumarlos cuenta dos veces lo mismo; y **se une entre cargas de página**, no se toma la mejor, porque un módulo compartido ejecuta funciones distintas en cada pantalla. **Tres estados, y el tercero es el que importa**: `ejercitado`, `rozado` (se carga pero casi nada suyo corre) y **`sin conducir`**, que **no es «0 %»** — es que ninguna pantalla de ningún caso lo carga, y confundirlo con un cero afirmaría que se midió algo que nadie miró. El umbral del `rozado` (25 %) es la parte discutible y va declarada, como `SEMANAS_TOLERADAS`. El artefacto lleva su `medidoEn: {commit, fecha}` dentro y el inventario **compara ese commit contra HEAD**: una cobertura medida sobre otro commit se lee como un hecho de hoy y ya no lo es. Medido el 2026-09-16 con los dos casos: 10 módulos ejercitados, **4 rozados** —`comparador.js` al 4 %, `calculadora.js` al 6 %— y 11 sin conducir. De paso corrigió una suposición de la propia propuesta que lo pidió: se dijo que `bom.js` no tenía ningún caso detrás y está al **54 %**, porque los dimensionadores pintan el BOM al cargar.

**Los tres scripts que abren un navegador resuelven Playwright en un solo sitio** (`scripts/ayuda/chromium.js`): `verificar-pantallas.js`, `contraste-motor.js` y `generar-manual-usuario.js` llevaban cada uno su copia. No era teórico — la de `contraste-motor.js` fijaba `/opt/pw-browsers/...` sin alternativa y pasaba **siempre** `executablePath`, así que habría fallado en el ejecutor de GitHub (donde Playwright se instala en `node_modules` y trae su propio Chromium) justo al llevar el contraste a CI. El orden de búsqueda es el que ya usaban los dos que funcionan: `require('playwright')` **primero** —que es lo que hay en un ejecutor—, luego la ruta global de este entorno; y para el ejecutable, la primera ruta conocida que **exista**, o ninguna, dejando que Playwright use el Chromium que él mismo descargó.

**`npm run contraste` en detalle.** Nació como un script suelto para el Multi-Underlay Builder de Fortinet y al llegar el segundo caso se partió en un **arnés** (`scripts/contraste-motor.js`) más **casos declarados** (`scripts/contrastes/*.js`), porque copiar el archivo es como `llevarABom` acabó en seis copias que no hacían lo mismo. Cada caso declara su línea base —**embebida, no en un archivo de datos**: es un hecho histórico medido sobre un commit concreto, y un fichero regenerable se regeneraría justo cuando el contraste fallara— más cómo traducir un escenario a los controles de *su* pantalla. **No generaliza de más a propósito**: el arnés no intenta adivinar campos comunes, porque un traductor que aceptara campos que una página no tiene acabaría rellenando controles inexistentes, que es el fallo que el gancho `caudal(page)` de `verificar-pantallas.js` existe para evitar. Dos casos hoy: `fortinet` (el builder no cambia el dimensionamiento; ocho escenarios más las seis migraciones de enlace v1) y `nokia-sr` (la regla de puertos al subir al módulo compartido). El segundo cazó dos tildes perdidas en texto visible el mismo día que se escribió.

**`npm run vigia` avisa cuando la fuente de un dato cambia, y ahora no se le olvida.** Este catálogo se verifica contra documentos que los fabricantes actualizan sin avisar, y hasta ahora la única forma de enterarse era que alguien volviera a mirar. El vigía compara el SHA-256 de cada URL de `FUENTES` contra `fuentes.lock.json` y reporta. **No extrae nada**: la lectura sigue siendo humana y el dato entra por `npm run cps` / `juniper` / `huawei`, que contrastan antes de escribir — automatizar la extracción de una tabla de PDF es justo donde se cuelan las filas desplazadas. `.github/workflows/vigia-fuentes.yml` lo corre cada lunes y abre (o comenta) un issue cuando algo cambia o no se pudo leer. **Un documento inalcanzable no es un documento sin cambios**, y el informe los distingue: desde este entorno los seis dan 403 por política de egreso, y eso se reporta con su código en vez de darlos por buenos. **Y un 403 tampoco prueba quién bloquea (pendiente 38, medido el 2026-09-16).** Tres fuentes daban 403 incluso desde Actions y de ahí se dedujo «es el fabricante». Las tres URL terminaban en `/`: no eran documentos sino **directorios**, y un CDN niega un listado por configuración sin bloquear a nadie. Las dos hipótesis se distinguen con un **grupo de control**, que es lo que hace `npm run candidatas` (`scripts/probar-candidatas.js` + `candidatas-fuentes.yml`): junto a cada URL bloqueada se pide un **archivo** del mismo dominio —y donde se puede, del mismo directorio— que el repositorio ya sabe que se descarga. Resultado: en las dos de Juniper el control respondió **200** y la carpeta 403, así que era la forma de la URL y se corrigieron con documentos que sí responden; en la de HPE el control también dio 403, así que ahí **sí** es el fabricante — y eso ahora está medido en vez de supuesto. La lista de URL bloqueadas se cruza contra `FUENTES` para que no se pudra como `CISCO_EOL_MODELS`.

**El tercer estado del lock (2026-09-14), y por qué era el defecto más caro del repositorio.** `--escribir` guardaba el hash nuevo de **todo** documento legible, incluidos los que acababa de marcar `CAMBIÓ`. Como el lock es su única memoria, la semana siguiente comparaba contra el hash que se acababa de tragar, decía «sin cambios» y **se ponía en verde solo**: la obligación de que una persona abriera el documento vivía siete días en un comentario de GitHub y desaparecía. No era un comprobador inerte como `CISCO_EOL_MODELS` — era peor, porque se curaba activamente. Medido: el boletín EOL de Cisco cambió en **tres mediciones consecutivas** (`48829947` el 02-sep, `4734ea1e` el 07-sep, `f57ff23f` el 14-sep) sin que nadie lo leyera, y cada semana se reportaba como hallazgo nuevo porque cada semana se borraba el anterior. El vicio es el conocido aquí: **dos estados donde hacen falta tres**. Ahora el lock separa `hashVerificado` (el último que **una persona** contrastó; es contra este que se compara y no se mueve solo), `visto` (lo último que el vigía vio) y `pendienteDesde` — que **no se reinicia** si el documento vuelve a cambiar, porque mide cuánto lleva sin revisar y no cuándo se vio. Se limpia con **`npm run vigia -- --revisado <fabricante> <url>`**, que es un acto humano y deja diff en git, igual que quitar una fuente de `legacyData/fuentes.js` exige un commit. **Las páginas `estable: false` sí se absorben, a propósito**: su hash varía en cada petición, y retenerlas las dejaría pendientes para siempre — el aviso en falso que ese campo existe para evitar. **Y desde el 2026-09-14 qué cuenta como «varía en cada petición» se mide en vez de declararse.** Ese campo se ponía a mano y nadie lo re-comprobaba —el modo de fallo de `CISCO_EOL_MODELS`—, así que **`npm run vigia -- --sondeo`** pide cada URL **dos veces** con segundos de diferencia: lo que cambie entre ellas no puede ser un cambio del fabricante. Compara los bytes y el **texto** (sin `script`, sin `style`, sin etiquetas) por separado, y cuando el texto difiere imprime el primer fragmento discrepante, porque «no coincide» sin decir en qué no se puede accionar. `.github/workflows/sondeo-fuentes.yml` lo corre desde Actions, que es donde hay salida. **La primera corrida encontró los dos errores posibles a la vez:** el boletín EOL de Cisco, declarado `estable: true`, devolvió los mismos 173.911 bytes con hash distinto y el mismo texto —sus tres semanas de «cambios» eran falsas alarmas—; y el EOL de Juniper, declarado `estable: false`, devolvió bytes idénticos, o sea que estaba **callado sin motivo** y un boletín nuevo no habría alarmado. De ahí que **el vigía vigile ahora el texto en las fuentes HTML y los bytes en los PDF**, con `clase` guardada en el lock: cuando cambia la unidad de medida eso **no** es un cambio del documento sino una línea base nueva, y se dice en el informe en vez de callarlo — un rebase silencioso es indistinguible de una alarma que alguien apagó. El riesgo de normalizar es tapar un cambio real, y lo que lo impide es una prueba: ya en texto, una diferencia de texto vuelve a ser `CAMBIÓ`. **Lo que no se midió es la estabilidad de un día para otro** —dos peticiones con 15 s de diferencia no dicen nada de eso—, así que MikroTik, las páginas de HPE y la de Nokia siguen en `estable: false` hasta que las corridas semanales acumulen evidencia: medir una cosa y afirmar otra es como se llega a un campo puesto a ojo. `test/vigia-lock.test.js` lleva el sabotaje dentro: reproduce la versión que absorbía y exige que produzca el verde falso, así que si alguien «simplifica» el tercer estado hasta volver a esa forma, la prueba deja de distinguirlas y salta.

**Lo pendiente se ve donde se mira y frena donde importa.** `npm run catalogo` gana la sección «FUENTES QUE CAMBIARON Y NADIE HA CONTRASTADO», y `test/fuentes-pendientes.test.js` la convierte en freno pasadas **4 semanas** (`SEMANAS_TOLERADAS`), por la misma regla que las pantallas: el inventario se corre cuando alguien se acuerda, `npm run verificar` corre en cada push. El umbral es la parte discutible y va declarada — sin él, que Fortinet publique un PDF un martes bloquearía trabajo que no tiene nada que ver; con él, hay un mes de margen y aun así no se puede ignorar sin límite.

**Y cada fuente declara QUÉ campos respalda, no solo en prosa.** `cubre` se lee bien en pantalla pero no dice si un cambio toca tres campos o cincuenta y ocho modelos, y sin esa magnitud la cola de revisión se atiende por orden de llegada en vez de por lo que arriesga. `campos` lo declara y `npm run catalogo` lo cruza contra el catálogo de verdad: el boletín EOL de Cisco sale como «respalda `eolAnnounced` · 8 modelos», y ese 8 **sale del catálogo**, no de un número escrito a mano que se quedaría con los modelos de ayer. Tres reglas lo hacen dato y no adorno: un campo declarado tiene que existir en las claves reales de `MODELS`/`MODELS_ROUTER` de ese fabricante —declarar uno inventado rompe `npm run verificar`, comprobado saboteándolo—; **`campos: null` es «no consta», nunca «no afecta»**, el mismo tercer estado de `redund`, y obliga a declarar `dominio: 'precio'` (esas cifras viven en `cotizadorCatalog.js`, otra fuente de verdad) o un `porQue`; y la cola se ordena primero por vencimiento y después por cuántos modelos se quedan sin respaldo. Hoy 10 de 17 fuentes declaran su radio: las 7 restantes lo dicen en vez de rellenarse a ojo, porque mapear una fuente a un campo que no respalda manda a revisar las cifras equivocadas — el error del `noAplica` deducido.


Two constraints of the sandbox this repo is usually edited from, worth knowing before promising a verification you can't perform: `presales.up.railway.app` is blocked by egress policy in this environment specifically — GitHub Actions runners are not behind that proxy and reach it fine, which is what `.github/workflows/sonda-produccion.yml` uses to confirm `/salud` and `/login` respond after a deploy (2026-09-02, pendiente 4). That confirms the site is *alive*, not that a specific screen renders correctly.

**Y esa segunda mitad no necesita producción, que es el hallazgo que cerró el pendiente 4 (2026-09-04).** `DATABASE_PATH` va sin definir allí, así que la base es efímera y se resiembra desde `legacyData/` en **cada** despliegue: lo que pinta una pantalla es función del *commit*, no del entorno. Un arranque de ese mismo commit en el ejecutor de Actions renderiza exactamente los mismos datos que producción, y eso es lo que hace `pantallas.yml`. La alternativa que se estudió —un entorno de staging en Railway— se descartó por seguridad, no por coste: habría añadido **una segunda copia pública del catálogo de precios** tras una contraseña guardada en los secretos del repositorio (legibles por cualquiera que pueda empujar un workflow), para no ver nada que no se vea en el ejecutor; allí la clave la genera el propio job y muere con él. Las dos mitades son `sonda-produccion.yml` (el dominio está vivo: DNS, TLS, el edge) y `pantallas.yml` (las pantallas funcionan), y ninguna sustituye a la otra. Lo único que sigue sin automatizarse es el **juicio** —si la pantalla dice lo que se le quiere decir a un cliente—, y para eso están las capturas del artefacto en vez de tener que abrir el sitio. HPE/Aruba domains are also blocked from this environment, and behave inconsistently even from Actions — `public/datasheets/` ships empty because of it (see below). A 403 from this environment's own proxy is an organization policy denial: report it, don't route around it.

Because `DATABASE_PATH` is unset in production, the catalog database is ephemeral and reseeded from `server/seed/legacyData/` on every deploy. That is what makes catalog changes ship with no migration step — and also why the IA sync is disabled there.

## Architecture

Single Express process (`server/server.js`) serves both the JSON API (`/api/*`) and the static frontend (`public/`) — one Railway service, no client build, matching chikisdtv/credifuturo's production pattern (though they compile a React client; this project has none). Everything except the login page sits behind an auth middleware: API requests get a 401 JSON, navigations get redirected to `/login` with the original destination preserved.

- `server/usuarios.js` — almacén de usuarios y roles, y el único sitio que sabe cifrar y verificar una contraseña. Vive en un archivo JSON bajo `AUTH_STATE_DIR` (volumen persistente) y **no** en SQLite, porque esa base es efímera y se resiembra en cada despliegue. La primera vez que se lee y no existe, se construye desde la credencial compartida anterior o desde `AUTH_PASSWORD`: ese usuario pasa a ser el **administrador**, sin contraseña nueva que comunicar y sin acceso por defecto inventado. Sin archivo y sin `AUTH_PASSWORD` no hay administrador y en producción el servidor no arranca — fallo cerrado, deliberado. Los permisos (`herramientas`, `usuarios`, `sync`) se declaran rol por rol en `ROLES`, no se deducen del nombre. El rol `consulta` existe sin usuarios todavía: dar de alta al primero sin privilegios será añadir una fila, no rediseñar la autorización.
- `server/auth.js` — la capa de sesión y el freno a la fuerza bruta, sin dependencias nuevas (scrypt + HMAC del `crypto` de Node). El token pasó de `expiración.firma` a **`expiración.id.firma`**: la sesión dice quién es, y la clave con la que se firma se deriva de la credencial *de ese usuario*, así que cambiar una contraseña invalida solo sus sesiones y no las del resto. `usuarioDeSesion(req)` lo resuelve una vez y `server.js` lo cuelga en `req.usuario`; ninguna ruta vuelve a mirar la cookie. La defensa contra fuerza bruta sigue en dos capas: contador por IP más retardo global progresivo, porque detrás del proxy de Railway se comprobó que rotando `X-Forwarded-For` se obtenía cuota nueva por intento.
- **Autorización: `exige('permiso')` en `server.js`.** Añadir una pantalla protegida es añadir ese middleware, no recordar un patrón. Responde 403 en JSON a `/api/*` y redirige el resto. Ocultar un enlace en la interfaz es comodidad, nunca control: `/usuarios` exige el permiso en la ruta y devuelve 403 a quien la teclee sin tenerlo. **El permiso `sync` existió meses en `ROLES` sin que ninguna ruta lo exigiera** — un permiso que no se comprueba es un permiso que no existe, igual que el conjunto inerte de fuera de venta. Ahora `app.use('/api/sync', exige('sync'))` va delante del router, y al montarlo así apareció el segundo fallo: `exige` miraba `req.path`, que Express recorta al prefijo de montaje, así que la API se redirigía al portal y el navegador veía un 200. Usa `req.baseUrl + req.path`. Lo encontró `test/servidor-produccion.test.js`, la única prueba que arranca el servidor de verdad.
- **Nadie cambia la contraseña de otro, ni el administrador.** Esa ruta no existe a propósito. Reponer un acceso perdido se hace borrando `usuarios.json` del volumen, que exige acceso al servidor y deja rastro; al no existir el archivo, el almacén se reconstruye desde `AUTH_PASSWORD` con un único administrador.
- **Alta de usuarios: `POST /api/usuarios`, ya implementada.** La decisión pendiente era cómo llega la primera contraseña a la persona nueva; se resolvió así: `usuarios.crear()` la **genera** (24 caracteres, alfabeto sin `0/O/1/l/I` para leerla en voz alta sin ambigüedad) y la devuelve **una sola vez** en la respuesta — nunca se guarda en claro ni se registra en el log —, para que el administrador la comunique por un canal distinto al panel. La cuenta nace con `debeCambiar: true`, y ese campo no es un aviso descartable como `desdeSemilla`: un middleware nuevo en `server.js`, justo después del muro de sesión, bloquea cualquier pantalla que no sea `/cuenta` (403 en API, redirect en navegación) hasta que la persona cambie la clave de verdad, momento en que `cambiarPassword()` lo libera. Verificado de extremo a extremo en Chromium: alta → login con la clave temporal → intento de ir al portal rebotado a `/cuenta` → cambio de clave → acceso liberado. **El nombre de usuario ya no se compara exacto**: `usuarios.normalizarUsuario()` (minúsculas, recortado por los bordes, nunca el espacio interior) es la forma canónica que usan tanto `crear()` al guardar como `mismoUsuario()` al comparar en el login — «JMartinez» y «jmartinez» son la misma cuenta. El campo `nombre` (el que se muestra) no se toca: conserva su capitalización porque nunca autentica.
- `server/server.js` also sets a strict CSP via helmet (`script-src 'self'` — no inline `<script>`, no `onclick=`), drops `cors()` (the API is same-origin; the package itself was removed from `package.json` too, a dependency nobody requires is only supply-chain surface), and serves SheetJS at `/vendor/xlsx.js` from the `xlsx` dependency so `public/` doesn't carry a duplicated ~900 KB copy. **`xlsx` apunta a `npm:@e965/xlsx`**: el paquete `xlsx` de npm quedó abandonado en 0.18.5 con una vulnerabilidad alta sin arreglo, y el espejo mantenido trae el mismo `dist/xlsx.full.min.js` (credifuturo ya lo usaba). `sqlite3` va en la 6, que dejó de arrastrar la cadena de build vulnerable de la 5. `/vendor/headroom.js` follows the same pattern for [headroom.js](https://github.com/WickyNilliams/headroom.js) (hides/shows a fixed header on scroll direction) — installed and served, not yet wired into any page's markup; whichever page adopts it just needs `<script src="/vendor/headroom.js">` plus its own `new Headroom(el).init()` call, same as `js/fuentes.js` needing to join `PUBLICO` if a public page ever needs it before login.
- `server/models/` — Sequelize models. `Product` is the central table: `vendorId`, `model`, `category`, a `specs` JSON column (vendor/category-specific numeric fields — `fwd`, `ipsec`, `mpps`, `poe`, etc. — instead of dozens of nullable columns), `specSummary`, `priceDisplay`/`priceNumeric`, `eol`. `OpticCategory`/`Optic` and `Part` hold Huawei/Cisco optics and BOM parts (joined to `Product` via `ProductOptic`/`ProductPart`); `SupportTier` and `LicenseBundle` hold Hi-Care/SmartNet/FortiCare tiers and Cisco DNA/Fortinet FortiGuard bundles; `RoleRecommendation` backs the design-guide's per-role equipment picks; `SyncLog` records IA-sync runs.
- `server/services/catalogProjection.js` — the only place that shapes DB rows into the JSON each frontend page expects. One function per page (`toIndexPR`, `toCotizadorCatalog`, `toDimensionadorHuawei/Cisco/Fortinet/Mikrotik/Aruba`, `toGuiaRoles`) — this is what lets the frontend stay close to its original static-file logic: each page does one `fetch()` and gets back the exact shape its existing render code already expects. `/api/dimensionador/:vendor` picks the projection from a lookup table, so adding a vendor's sizing page means adding one projection plus one entry there.
- `server/routes/` — thin route handlers that call the projection functions above. `sync.js` handles AI synchronization via Anthropic's Claude API, using `multer` to accept multipart/form-data uploads (PDF/Excel datasheets) and `xlsx` for parsing spreadsheet catalogs.
- `server/services/aiSync.js` — handles the Anthropic API interaction (`claude-opus-5`), passing the full database and uploaded documents to Claude for intelligent catalog comparison and updates. **Analizar corre en cualquier entorno, incluida producción; escribir en la base, solo en local.** `server/routes/sync.js` separa las dos: `analyze` LEE el catálogo (y en producción es lo vigente, porque la base se resiembra desde `legacyData/` en cada deploy) y devuelve cambios sin escribir nada; `apply` ESCRIBE en la base y sigue respondiendo 503 en producción, porque esa base es efímera y el cambio se perdería. El camino durable no pasa por `apply`: se descarga la propuesta y `.github/workflows/aplicar-propuesta.yml` la aplica sobre `legacyData/` con anclaje y abre un PR — el token de escritura vive en Actions, nunca en este servicio (ver `docs/sincronizacion.md`). `GET /api/sync/estado` informa a la UI del entorno y de si hay clave, para no ofrecer un botón que va a fallar. **Sin `ANTHROPIC_API_KEY` `analyze` responde 503**, con un error propio (`SinClave`): aquí vivió un simulacro que devolvía propuestas inventadas con apariencia legítima —un «FortiGate 9000F» con precio— y se retiró porque es exactamente el dato falso con pinta de verdadero que este catálogo prohíbe. El tipo del adjunto lo decide `services/firmaArchivo.js` leyendo la firma del contenido (`%PDF`, `PK`, texto), no el mimetype del navegador; lo que no es PDF, XLSX ni CSV/TXT recibe 415. **La respuesta va con esquema, no con expresión regular**: `output_config.format` obliga a la forma exacta, así que el parser deja de ser una heurística que bastaba un corchete suelto para romper. Las instrucciones y el catálogo van cacheados (`cache_control`) por delante del adjunto, que es lo único que cambia entre llamadas. Catalog updates go through the seed files instead: analyse locally, carry the approved changes into `server/seed/legacyData/`, and deploy — con **`npm run propuesta`** (`scripts/importar-propuesta.js`) en vez de volver a teclearlas.
- **`npm run propuesta`: la IA propone, el importador aplica, el diff decide.** El botón «Sincronizar» escribía en la base local, que no es la fuente de verdad —producción se resiembra desde `legacyData/`—, así que lo aprobado había que volver a teclearlo: dos sitios con el mismo dato y un paso manual entre ellos. Este importador cierra ese hueco escribiendo sobre `legacyData/` para que lo que quede a revisar sea un diff de git. **Su anclaje es distinto al de `npm run juniper`**: allí el riesgo es la fila desplazada y el ancla son dos columnas que casen; aquí el riesgo es una propuesta obsoleta o inventada, y el ancla es el propio `oldValue` — *si la IA se equivoca sobre lo que el catálogo dice hoy, no hay razón para creerle lo que dice que debería decir*. Además exige URL de fuente oficial, rechaza lo que no cambia nada, y **las altas se reportan pero nunca se aplican solas**: dar de alta un modelo es justo donde entró el `FortiGate 2000F` inexistente que este catálogo ya sufrió.
- `server/fuentesSubidas.js` — **carga manual de la fuente oficial por fabricante, sin IA ni crédito.** Cada fabricante tiene en su pestaña «Fuentes y Referencias» un botón «Cargar fuente oficial» (permiso `sync`): sube el datasheet/lista de precios (PDF/XLSX/CSV/TXT, tipo decidido por firma de contenido) y la procedencia de ese fabricante se actualiza al instante — el documento aparece como fuente «Cargada» con fecha, hash y enlace. **Actualiza la procedencia, no reescribe las cifras**: subir no es contrastar, y estampar «verificado» sobre números que nadie comparó es la mentira que este catálogo prohíbe (para las cifras sigue el importador o la IA). Los archivos viven en el volumen persistente (`AUTH_STATE_DIR/fuentes/`), como `usuarios.json`, no en la base efímera, así que sobreviven a un deploy; el nombre en disco lo genera el servidor, nunca el del archivo subido. Rutas: `POST /api/fuentes/:vendor`, `GET /api/fuentes/:vendor/documento/:id` y `DELETE /api/fuentes/:vendor/documento/:id` (permiso `sync`). **Solo se borra lo cargado, y eso es deliberado**: las fuentes de `legacyData/fuentes.js` muestran «en el código» en vez de un botón, porque viven en el repositorio y se quitan con un commit que deja diff — un botón que borrara la procedencia del catálogo sin rastro sería lo contrario de lo que esa pestaña existe para dar. `eliminar()` retira la entrada **aunque el archivo ya no esté** en el volumen: una fila que anuncia un documento oficial que no se puede abrir es un enlace roto presentado como procedencia. **Una vigente por fabricante** (decisión del dueño del repo, 2026-09-08): subir otra vez manda la anterior a un histórico plegado en vez de acumular dos filas «Cargada» iguales sin decir cuál manda — que es como se detectó, con la lista de precios de Fortinet. **Sustituir no es destruir**: la anterior conserva su archivo y sigue consultable, porque la lista de precios del trimestre pasado es justo lo que explica por qué una cotización de entonces decía otra cifra; para borrarla de verdad está el botón. Y si se borra la vigente, la más reciente que quede es promovida, porque un fabricante con documentos cargados y ninguno vigente sería un estado que la pestaña no sabría explicar. Y un **botón «Actualizar»** en los siete fabricantes vuelve a pedir `/api/fuentes` y repinta, porque el portal pinta esta pantalla una sola vez al cargarse y un documento subido o borrado desde otra pestaña no se veía hasta recargar entero. Ver `docs/sincronizacion.md`.
- `server/seed/legacyData/fuentes.js` — **la procedencia del catálogo, como datos y no como comentario.** Cada `legacyData/*.js` ya documentaba en su cabecera de qué documento y de qué fecha salen sus cifras, pero eso no lo ve ni la aplicación ni ninguna comprobación automática — y en una herramienta de preventa quien arma una propuesta está a punto de citar una cifra delante de un cliente. Aquí esa misma información se estructura, transcrita de cada cabecera y sin inventar nada: donde la cabecera **no** da fecha (MikroTik y Aruba), `fecha` queda en `null` y se declara. **Una fuente sin fecha no es una fuente reciente**, y tratarla como cero meses diría «recién verificado» justo donde no se sabe nada — el mismo tercer estado que protege `redund`. Se proyecta en `/api/fuentes`, el portal la pinta en la pestaña «Fuentes y Referencias» de los siete fabricantes, y el arranque avisa por consola de lo que supera los seis meses o no tiene fecha. El campo `hash` lo rellena `npm run vigia` desde fuera de este entorno. **Y desde el 2026-09-14 la pestaña trae una columna «Vigilancia»**, que responde una pregunta distinta de «Estado»: ese habla de la *antigüedad de lo transcrito* y esta de si *el documento de la otra punta sigue siendo el mismo*. Las dos pueden ser ciertas a la vez y leerse muy distinto delante de un cliente — hoy el Product Matrix de Fortinet sale «Vigente» (2 meses) y «Cambió · sin contrastar desde 2026-09-14». Tres estados y ninguno deducido: `verificada`, `cambió` (con desde cuándo) y `no comprobada`, que **nunca** es verde — cubre tanto una fuente sin URL pública que vigilar como una página `estable: false`, cuyo hash varía en cada petición y por tanto no dice nada del dato. - `js/aruba-reglas.js` — **las reglas puras del dimensionador Aruba que la auditoría del 2026-09-17 encontró rotas**, fuera de la página para poder probarlas en Node (UMD, mismo patrón que `motor-ingenieria.js`; global `ArubaReglas`): el tier de suscripción solo entre los que existen para el nivel (Foundation = 100 Mbps / 1 Gbps / ilimitado), la capacidad del gateway por sistema operativo (`porSo` en `aruba.js`: AOS 10 por defecto, AOS 8 en el selector `#soSeg`), el Boost como 30 % del tráfico de los túneles validado contra el Boost recomendado por HPE, y Dynamic Threat Defense como filtro duro (`dtd:false` en el EC-XS). Pruebas: `test/aruba-auditoria-fase1.test.js` y `test/e2e/e2e-auditoria-fase1.js`.
- `js/ficha.js` — the candidate picker and full spec sheet, shared by the five dimensionadores. The "Modelo recomendado" block is no longer a single fixed model: it is a `<select>` listing **every** model that meets the constraints, and choosing one re-renders the meters, the reasoning, the sizing summary, the licensing/support panels and the BOM tab for that model. Each page supplies a descriptor (`medidores`, `porQue`, `secciones`, `alCambiar`) built from its own vendor data — the module never computes a figure, it only presents. Sections are consistent across vendors: características, alimentación eléctrica, licenciamiento propuesto, software y soporte. **Elegido a mano y heredado no son lo mismo, y confundirlos convertía la selección en un trinquete.** La regla era «conservar la selección mientras ese equipo siga cumpliendo», y como cumplir es capacidad ≥ requerimiento, un equipo grande cumple para **todo** requerimiento menor: medido en el navegador, se elegía un 7121F a 20 Gbps, se bajaba a 50 Mbps y seguía en pantalla el 7121F con el 30G como recomendado. La selección solo subía. Y lo grave no era la elección manual sino que la **heredada** —la que el propio módulo había dejado en el render anterior— se reciclaba con ese mismo criterio, así que el recomendado solo aparecía en el primer render de la página. Ahora solo persiste lo que alguien eligió de verdad: el desplegable, o una reposición desde la URL o el almacenamiento, que también es la elección de alguien. Lo heredado sigue siempre al recomendado. La elección deliberada se marca en pantalla, se suelta cuando ese equipo deja de cumplir, y tiene salida explícita — el botón «Volver al recomendado», porque apartarse era una puerta de un solo sentido en una lista de 58 equipos.
- **Semáforo de ciclo de vida: el verde se gana, no se hereda (pendiente 34, 2026-09-16).** `FICHA.cicloHtml` es la única implementación y la usan los siete. **Cinco estados**: fuera de venta (fecha de último pedido vencida, o `eol` binario —que declara que el catálogo *no trae* la fecha—), fin de venta **anunciado y todavía pedible**, línea anterior, vigente, y el tercer estado. Vivía dentro de `dimensionador-aruba-edgeconnect.js` con el **verde como rama por defecto**, así que no era que portarlo *fuera* a pintar verde falso sobre 131 modelos: ya lo estaba haciendo sobre los 25 de Aruba. **La ausencia de un boletín no es prueba de vigencia**, solo lo es si alguien mira los boletines de ese fabricante — y eso ya estaba declarado en `legacyData/fuentes.js`: una fuente cuyo `campos` incluya `eolAnnounced` es exactamente «hay un documento de fin de venta contrastado, de esta fecha». Se reutiliza esa declaración (`respaldoCicloVida()`, proyectada en `/api/dimensionador/:vendor`) en vez de escribir una segunda lista de fabricantes, que es como se desincronizan dos sitios con el mismo dato: hoy **Cisco y Juniper** pueden pintar verde, y la ficha dice contra qué documento y de qué fecha; los otros cinco declaran «el catálogo no trae el ciclo de vida». La página lo informa **una vez** con `FICHA.fijarCicloVida(data.cicloVida)` tras su fetch, y no en cada `FICHA.render`: hay veinte puntos de llamada entre los siete contando los estados vacíos, y pasarlo en todos es como `llevarABom` acabó en seis copias. De paso corrigió un defecto que la copia de Aruba tenía y `FICHA.rango()` no: pintaba de **rojo** un fin de venta anunciado que aún no había vencido, cuando hasta esa fecha el equipo se pide con normalidad.
- **Configuración de puertos: la regla la aporta Nokia, no Aruba (pendiente 35, 2026-09-16).** `FICHA.seccionPuertos` en los siete. `legacyData/nokia.js` es el único catálogo de los ocho que modela los puertos como **dato** y no como texto, con dos reglas que ningún otro tenía resueltas: las configuraciones son **alternativas y no acumulables** («36x100GE o 12x400GE» nunca son 48 interfaces) y **un chasis modular no publica densidad** («7 slots IOM» dice cuántas tarjetas caben, no cuántos puertos salen), así que se aparta con su motivo. El flujo de `docs/portabilidad-aruba.md` no es «Aruba enseña a los siete»: la capa común es algo **a lo que cada fabricante aporta lo que ya resolvió**. **Los otros seis no reciben un panel vacío**: traen los puertos como texto libre (`ports` en Cisco/Huawei/MikroTik, `ifaces` en Fortinet/Juniper/Aruba), se muestran y la ficha **declara** que no están estructurados y que por eso no se puede contrastar densidad contra un requerimiento — la diferencia entre «este equipo no tiene puertos» y «el catálogo no sabe contarlos». **Una `notaPuertos` explícita gana al texto libre**: el 7250 IXR-e publica velocidades pero no densidad, y pintar su `ifaces` al lado de esa nota lo haría leer como una densidad. **No audita nada contra un escenario**: la de Aruba (cuántos enlaces caben en el chasis) responde otra pregunta y se queda en su página.
- **Referencias de pedido: que hay que PEDIR, no solo que equipo elegir.** `server/services/referencias.js` + la sección que `js/ficha.js` pinta en los siete dimensionadores. La ficha mostraba el rendimiento de un equipo y **ni un solo número de parte**, así que quien armaba una propuesta tenía el modelo y luego iba a buscar el SKU a otro sitio — y las 28 referencias que Aruba ya traía estructuradas no se veían en ninguna pantalla. Fortinet aporta **6.849 referencias** (hardware, bundles de FortiCare/FortiGuard, licencias y SaaS) con descripción y precio de lista, extraídas de la misma price list que respalda los precios con **`npm run skus`** (`scripts/importar-skus-fortinet.js`), que ancla cada bloque contra el `hwSku` y el precio ya verificados antes de aceptarlo. **Van bajo demanda y por modelo** (`GET /api/referencias/:vendor/:modelo`): son 774 KB en total y meterlas en el payload del dimensionador cargaría todo eso en cada visita para mostrar como mucho las de un equipo; por modelo son ~12 KB. Se sirven desde `legacyData` sin pasar por la base, con el precedente de `toFuentes`. **Lo que cada fabricante tiene es distinto y se dice**: Aruba trae variantes **sin número de parte** (HPE no lo publica, igual que no publica precios) y se presentan como tales; Cisco solo el SKU de cabecera de 8 de sus 21; Huawei, MikroTik, Juniper y Nokia no traen ninguna y **la sección lo declara** en vez de dejar un hueco que se lee como «este equipo no necesita nada». Verificado en Chromium: el buscador filtra sin perder el foco, los chips acotan por tipo, y al cambiar de equipo **los SKU cambian** — el conteo no lo probaba, porque 60F y 61F traen 79 referencias cada uno.
- **La Calculadora de Throughput gana el perfil de inspección TLS, y dice cuánto del catálogo puede responder cada capa (2026-09-23).** Ofrecía cinco perfiles y ninguno era el de descifrado HTTPS, así que quien preguntaba «¿qué equipo para esto con inspección TLS?» en el portal recibía **la respuesta calculada sobre Threat Protection** — el mismo defecto P0 que el dimensionador de Fortinet arrastró hasta el día anterior, pero en la pantalla de portada. No se podía cerrar antes: el catálogo solo traía `ssl` de 9 modelos. **El perfil NO es un peldaño más de la escalera**: descifrar TLS es otra ruta de proceso, y el cociente ssl/tp de este catálogo va de 0,52 a 1,18, así que sustituir una cifra por la otra **se equivoca en las dos direcciones** — medido en esta pantalla: a 175 Mbps Threat Protection proponía un **30G** que solo hace 400 Mbps de TLS (**corto**), y a 500 Mbps proponía un **70G** donde el **50G** cumple porque aguanta más TLS que TP (**sobredimensionado**). Un solo lector en el mapa de capas, a propósito: añadir los otros siete con la cifra de otra capa sería el derate recién retirado. **Y entra con él una línea de cobertura encima de la lista, para los seis perfiles**: `CALC.cobertura()` cuenta contra el catálogo —nunca contra una lista escrita a mano, que es la forma de `CISCO_EOL_MODELS`— cuántos fabricantes y cuántos modelos publican esa capa, y lo dice **antes** de la tabla. El panel de apartados ya lo contaba pero va al final, así que primero se leían tres equipos de un fabricante y solo al bajar se descubría que los otros siete no se comprobaron; con inspección TLS compite **1 de 7 fabricantes**, y sin ese encabezado cinco equipos se leen como «no hay equipo» cuando lo que pasa es «no hay dato» — dos conclusiones que mandan a sitios opuestos. Lo guardan `test/servidor-produccion.test.js` (que interroga al servidor real, porque `ssl` llega a `/api/catalog` por la **fusión** de la siembra y un mapa escrito contra `indexPR.js` apartaría el perfil entero) y el contraste `calculadora-ssl`, que conduce la pantalla con los dos escenarios opuestos más un control de reenvío. **El caso se endureció saboteando**: la primera versión pasaba en verde con el derate dentro, porque los dos modelos sin cifra (100F y 200F) no son el más pequeño que cumple en ninguno de los seis escenarios — la señal que sí cambia es que **Fortinet aparezca entre los apartados de su propio perfil**, y esa es la aserción que quedó.
- `js/calculadora.js` — **qué capa se dimensiona en la Calculadora de Throughput y qué se hace con lo que el catálogo no publica**; el pintado vive en `js/index.js`. Elegía equipo con una sola línea —`const cap = profile==='ipsec' && d.ipsec>0 ? d.ipsec : d.tp`— y `d.tp` es la cifra de **portada** de cada catálogo, así que el perfil «SD-WAN / NGFW» no miró la cifra de NGFW ni una sola vez: medido en el navegador con los valores por defecto de la pantalla (2,6 Gbps) proponía un FortiGate 30G, que hace 570 Mbps de NGFW — **factor 4,6x por debajo**, el mismo modo de fallo que la auditoría de FortiGate documentó con 14,3x. Y un equipo **sin** cifra de esa capa no se apartaba: se juzgaba por su forwarding, así que para 2,6 Gbps de IPsec proponía un Nokia 7220 IXR-D1 —un leaf de fabric de datacenter— y un Aruba EC-S cuyo IPsec en este catálogo es `0`. **La regla es una: se dimensiona con la cifra de la capa que pide el perfil, y si el catálogo no la trae, el modelo se aparta con su motivo** — nunca se sustituye por la de otra capa, que es justo lo que produce propuestas cortas por un orden de magnitud (misma regla que `dimensionador-juniper-srx.js` aplica a `fw`). Los apartados se cuentan por fabricante, con su motivo y el enlace a su dimensionador, para que una lista corta se explique en vez de leerse como catálogo completo. Seis perfiles, que son seis preguntas distintas sobre el mismo equipo: reenvío/firewall, IPsec, SD-WAN, con inspección (NGFW/IPS), inspección completa (Threat Protection/ATP) e **inspección TLS** (que no es la más profunda de la escalera sino otra ruta: ver la entrada de arriba) — en un FortiGate 120G son 39, 35, —, 3,1 y 2,8 Gbps. **El mapa de capas se escribe contra `/api/catalog`, no contra `legacyData/indexPR.js`**: `seedCatalog.js` funde en la misma fila el catálogo del portal y el del dimensionador de ese fabricante, así que el `sdwan` de Cisco es el texto «Sí» en el primero y un **número** en la segunda. Escribirlo contra `indexPR.js` apartó los 19 modelos de Cisco «porque el catálogo no lo publica» — un «sin dato» falso, el mismo error que el «IPS: no aplica» del Catalyst 8300 en el comparador. Lo guarda `test/servidor-produccion.test.js`, que interroga al servidor de verdad: un modelo solo puede apartarse si el campo del que sale esa capa está vacío **en su fila**. La exportación CSV se arma con los datos (con la capa dimensionada y los apartados con su motivo) y no rascando el HTML ya pintado, y la lista de fabricantes se deriva del catálogo, no de un array escrito a mano.
- `js/comparador.js` — **qué se compara en el Comparador de Equipos y cómo se resuelve cada casilla**; el pintado vive en `js/index.js`. Mostraba **seis filas** —serie, segmento, throughput, IPsec, SD-WAN y puertos— mientras `/api/catalog` entrega entre 15 y 29 campos por fabricante: el dato no faltaba, `buildAll()` lo tiraba al normalizar los ocho catálogos a una forma común mínima. Ahora son ~30 filas en siete secciones, en **matriz** (una fila por atributo, una columna por equipo) y no en tarjetas — con tarjetas, comparar un dato obligaba a buscarlo en cuatro sitios y compararlo de memoria, que es lo que un comparador tiene que ahorrar. **Tres estados por casilla:** `dato`, `sinDato` (el catálogo no lo trae — dice algo del catálogo, no del equipo) y `noAplica` (el concepto no existe para esa clase de equipo, **con su motivo**). `noAplica` se declara a mano en `NA`, nunca se deduce de que a un fabricante le falte el campo: la primera versión hacía eso y decía «IPS: no aplica» de un Catalyst 8300, que hace IPS con Snort desde IOS XE — el mismo error que `redund` evita al no leer `undefined` como `false`, y aquí peor, porque descarta un equipo por algo que sí sabe hacer. **No se corona un ganador entre cifras que no se miden igual:** las filas de rendimiento llevan `mismaBase`, así que la flecha verde solo aparece entre equipos del mismo fabricante — marcar los 24 Gbps de firewall de un SRX como mejores que los 5 Gbps de forwarding de un Cisco contradiría el aviso que la propia pantalla muestra encima de la tabla. Las filas que no dependen de la base (sesiones, APs, vatios) sí se comparan entre fabricantes. El interruptor «solo diferencias» esconde las filas que coinciden, y la tabla se repinta al cambiar cualquier control sin volver a pulsar el botón.
- `js/estado.js` — el escenario de cada pantalla vive en la URL y en el navegador. Se midió el problema antes de escribirlo: recargar el cotizador vaciaba un BOM con equipos dentro, y copiar la URL del dimensionador con 2.500 Mbps le mostraba 500 Mbps y otra recomendación a quien la abría. **La URL manda cuando trae parámetros** (alguien te pasó un enlace) y el almacenamiento local cubre el resto (vuelves a la pestaña de ayer): resuelven cosas distintas y hacen falta las dos. Solo se serializa **lo que difiere del valor por defecto**, así que el enlace es `?bw=2500&profileSeg=ips` y no una tira de veinte pares — se lee y se edita a mano, que es el motivo de elegir querystring y no un blob codificado. Incluye `verdict-sel`, el equipo elegido: sin él, el receptor podía ver otro modelo, porque `ficha.js` conserva la elección **deliberada** mientras siga cumpliendo — y reponer `verdict-sel` cuenta como tal, que es justo lo que hace que el enlace llegue con el equipo del emisor y no con el recomendado del receptor. Se integra sin tocar el motor de las páginas: repone los valores antes de que corra su script y, para los grupos `.seg`, dispara un click sintético después, porque ahí la elección vive en una variable de la página y solo su propio manejador la actualiza. Verificado de extremo a extremo: un enlace abierto sin sesión pasa por el muro de login conservando el querystring y aterriza en el escenario exacto.
- **Un enlace compartido que llega con parámetros que la pantalla ya no entiende lo dice.** `ESTADO.vincular()` compara lo que trae la URL contra los campos declarados y devuelve `ignorados`; `ESTADO.avisoOrigen()` los **nombra** bajo el botón «Copiar enlace». Esto cubre para los *parámetros* lo que `RENOMBRADAS` en `server.js` cubre para el *nombre del archivo*, y el hueco era real: el 2026-09-13 el dimensionador Aruba retiró su campo `#bw`, y los enlaces ya pegados en chats solo se salvaron porque alguien escribió a mano `migrarEstadoV1()` para esa página — la regla general no existía, así que cualquier otra pantalla que renombre un control deja al receptor viendo otro escenario **sin una sola señal**. Tres decisiones que lo hacen útil en vez de ruido: se avisa **aunque no haya ningún campo reconocible** (es el caso peor, la pantalla sale en blanco y sin el aviso no habría nada que lo explicara); **no** se denuncia lo que la página sabe migrar, que declara en `cfg.migrados` —Aruba pasa su `PARAMS_V1`, la misma constante que usa la migración, porque dos listas iguales en dos sitios se desincronizan— ni las marcas de campaña (`utm_*`, `gclid`…), que nunca fueron escenario; y la lista se acota a seis nombres, porque un párrafo que nadie lee no avisa. Los nombres se escapan antes de pintarse: la URL la escribe quien manda el enlace, y apoyarse en la CSP para eso sería confiar la corrección de una pantalla a una cabecera de otra capa.
- `js/fuentes.js` — las tipografías dejan de bloquear el render. **Medido, no supuesto:** cronometrando la navegación entre herramientas salieron 12,5 s por página; la sospecha razonable era el servidor, pero la API respondía en 7 ms. Lo que costaba eran los 12,5 s de espera de la hoja de Google Fonts, que el navegador trata como recurso bloqueante. Las hojas se marcan `media="print" data-fuente` en el HTML —el navegador las descarga sin bloquear— y este módulo las devuelve a `all` cuando llegan. El truco habitual (`onload` en el `<link>`) necesitaría JavaScript en línea, que la CSP prohíbe. Con esto el DOM queda listo en **31 ms en vez de 12.529**. No es solo un artefacto del entorno: esta herramienta se abre desde redes corporativas, y un proxy que bloquee dominios de Google es un escenario normal. `/js/fuentes.js` va en `PUBLICO` porque la página de acceso usa las mismas tipografías; si quedara tras el muro, el navegador recibiría HTML donde espera JavaScript.
- `js/contraste.js` — **qué cuenta como cambio al subir una fuente tabular, y por qué es una vista previa y no el importador**; el parseo (SheetJS bajo demanda) y el pintado viven en `js/index.js`. Al cargar una fuente oficial Excel/CSV se abre en el acto una ventana que la contrasta con el catálogo vigente **en el navegador, sin IA y sin crédito**. Devuelve cuatro montones porque son cuatro cosas distintas: **cambios** (el modelo existe y una columna reconocida trae otro valor —comparado por valor, no por formato: «300» y «300 Mbps» no son un cambio), **altas** (modelo que no está en el catálogo: se reportan pero **nunca** se aplican solas, la misma regla del importador, porque dar de alta es donde entró el `FortiGate 2000F` inventado), **sin cambio** (solo se cuentan) y **columnas ignoradas** (cabeceras que no casan con ningún campo: se **listan**, no se adivinan —reconoce una columna solo si su cabecera es un campo real o un alias explícito cuyo campo existe para ese fabricante). No escribe nada: desde la ventana se marcan los cambios y se **descarga la propuesta** con la forma que consumen `npm run propuesta` y `aplicar-propuesta.yml`, así el cambio pasa por el mismo anclaje (`oldValue` que casa con el catálogo de hoy, URL oficial) y por un PR revisable. **Y casa por dos claves distintas, porque son dos documentos distintos**: una hoja de especificaciones nombra el equipo («FortiGate 30G») y una lista de precios lo nombra por su referencia de pedido («FG-30G», que aquí es `hwSku`). Sin la segunda, subir la lista de precios real de Fortinet daba «no se encontró una columna de modelo» y no validaba nada aunque el documento fuera el correcto. **Una fila que no casa significa cosas distintas según la clave**: por nombre es un alta candidata y se reporta; por SKU no, porque una price list trae miles de referencias de licencias, soporte y accesorios que no son equipos — ahí solo se cuentan, o los pocos cambios reales quedarían sepultados bajo miles de líneas de ruido. Los **precios se listan para revisar pero no se publican por esta vía**, y la ventana lo dice: viven en `cotizadorCatalog.js` y el importador los aparta a propósito. **Un PDF no se contrasta aquí**: extraer una tabla de un PDF sin equivocar de fila es justo lo que este repositorio no automatiza —la ventana lo dice y remite a la IA o a los importadores—. Verificado de extremo a extremo en Chromium (login → pestaña de fuentes → subir CSV → la ventana detecta el cambio de un AR611 y reporta el alta y la columna ignorada). Ver `docs/sincronizacion.md`.
- `js/navegacion.js` — **la barra de fabricante, y por qué la continuidad es de navegación y no de archivo.** Las herramientas de un fabricante estaban repartidas entre el portal (catálogo y fuentes) y su propia página (dimensionador, BOM y licencias), y no había forma de pasar de un fabricante al siguiente sin volver al portal y buscarlo en la barra lateral. La barra se pinta sola en el portal y en los ocho dimensionadores —cada página solo carga el script; **detecta dónde está por su propia URL**, sin una marca que se desincronice al renombrar un archivo— y da **← anterior / siguiente →** con el nombre del destino a la vista, el paso actual marcado, el contador «3 / 7» y `Alt`+flechas (con `Alt` a propósito: las flechas solas las usan los campos numéricos y los desplegables de estas pantallas). **Conserva el paso al cambiar de fabricante**: desde el dimensionador de Fortinet, «siguiente» lleva al dimensionador de Juniper y no a su portada — eso es lo que la convierte en un recorrido y no en un menú. **Por qué no se fusionaron los ocho dimensionadores en `index.html`**, que era la petición literal: los ocho tienen un `#bw`, un `#verdict` y un `#pane-bom`, así que juntarlos habría metido ocho motores de dimensionamiento en el mismo espacio de identificadores y en el mismo estado global. La continuidad que hacía falta es de navegación, y así el riesgo es una barra que se pinta mal, no un dimensionador que calcula mal. **Se repinta observando la clase de las secciones** (`MutationObserver`) en vez de envolver `go()`: parchear una función de otra página se rompe en cuanto alguien la renombra. Y **fuera de un fabricante la barra se vacía** — dejarla puesta haría que el comparador siguiera anunciando el fabricante del que vienes.
- `js/procedencia.js` — la pestaña «Fuentes y Referencias» como módulo compartido: leer `/api/fuentes`, pintar la tabla de procedencia, subir la fuente oficial, borrarla y contrastarla en el acto. **Vivía embebido en `index.js`**, atado a las siete cajas `[data-procedencia]` del portal; se extrajo cuando el dimensionador de Fortinet ganó su propia pestaña de fuentes (2026-09-09), porque duplicarlo allí lo habría hecho divergir del portal — la misma razón por la que `bom.js`, `ficha.js` y `estado.js` ya eran compartidos, y el mismo modo de fallo que tuvo `llevarABom` en seis copias. Lo cargan el portal y los siete dimensionadores. Lo único que cada página aporta es de dónde saca sus modelos (`PROCEDENCIA.registrarModelos`), porque el portal tiene los siete fabricantes tras `/api/catalog` y un dimensionador solo el suyo tras `/api/dimensionador/<vendor>`; el resto es idéntico. Se autoinicia, como `tabla.js` y `navegacion.js`.
- `js/tabla.js` — ordenación por columna con solo marcar `<table data-ordenable>`. El tipo de cada columna **se deduce del contenido** y una columna es numérica si lo es la mayoría de sus celdas, no la primera —basta un «Consultar» en el precio para equivocarse—; las celdas sin dato van siempre al final, porque «sin dato» no es ni el mayor ni el menor y tratarlo como cero mentiría. **La coma es separador de miles y el punto es decimal**, que es como está escrito este catálogo (`~ $5,999`, `512,000`, `6.4 Tbps`): al revés, 5.999 dólares valían menos que 29 — se detectó ordenando la tabla de MikroTik.
- **Traspaso dimensionador → cotizador** (`BOM.enviarACotizador` / `recogerEntrada` en `js/bom.js`). Dimensionabas un FortiGate 200G y luego lo buscabas a mano entre los 154 equipos del cotizador. Ahora hay un botón «Enviar al cotizador» en la barra de acciones del BOM que comparten las seis páginas. **El dimensionador solo dice QUÉ equipo, no construye la línea**: el precio, el fabricante y el texto comercial salen de `CATALOG`, que es la fuente de verdad del cotizador — si los rellenara el dimensionador habría dos sitios con el mismo dato. Los dos catálogos nombran distinto (`SRX380` frente a `Juniper SRX380`, `EC-XS` frente a `Aruba EC-XS`), así que se casan normalizando —minúsculas, sin separadores, sin prefijo de fabricante— en vez de mantener a mano una tabla de equivalencias. Lo que llega **se suma** al BOM guardado, no lo sustituye. Y si el modelo no está en el catálogo del cotizador se dice: la causa casi siempre es que esté fuera de venta, porque el cotizador solo lista lo vigente mientras el dimensionador sí lo muestra como referencia.
- **Y desde el 2026-09-18 viaja el BOM entero, no solo el equipo (A6 de la fase 2).** Medido antes de tocar nada: el BOM de un FortiGate 200G a 2.500 Mbps son cuatro líneas por **$38.088,20** y al cotizador viajaba solo el equipo, $11.477 — el 70 % de la cotización se volvía a teclear a mano. **No hizo falta un canal nuevo**: el cotizador ya ingiere líneas que no están en `CATALOG` por la vía de las referencias, y una licencia calculada por el dimensionador es exactamente eso. La regla es **categórica y no una lista enumerada** —viaja toda fila cuyo `cat` no sea `'Equipo'`—, así que Boost, DTD/SSE, Central, ópticas o lo que añada cualquier motor viajan sin tocar este módulo. **La fila del equipo se excluye a propósito**: el hardware sigue viajando solo como nombre porque su precio lo pone `CATALOG`, y mandarlo además como referencia lo cotizaría dos veces — el fallo de los $38.088,20 → $49.565,20 que `renderTabla` ya avisaba para las referencias añadidas a mano. **La `nota` de cada fila no viaja**, decisión declarada: lleva texto interno del dimensionador y la cotización la ve el cliente. Y **falla cerrado**: sin fila `cat:'Equipo'`, o si esa fila no es el modelo que manda la página (el desplegable del BOM cotiza cualquier equipo a propósito), viaja solo el equipo y el botón dice por qué — una cotización corta y declarada antes que una incoherente en silencio. **El caso que lo guarda se descubrió saboteando**: quitar la condición `cat !== 'Equipo'` pasaba en verde porque la defensa de segundo orden (el SKU repetido) tapaba el fallo, y cuatro de los seis dimensionadores que montan el botón —Huawei, Juniper, MikroTik, Nokia— traen su fila de hardware con `sku: null`, donde la categoría es la **única** defensa.
- **Los dos fallos de dinero que salieron con A6 estaban en la ingesta del cotizador, no en el traspaso.** Los dos preexistentes, los dos invisibles desde `curl` y desde una función pura, y los dos en la cifra que se pone delante de un cliente. **(1) Toda cotización empezada desde un dimensionador salía al doble**: la fusión con el BOM restaurado corría también cuando no había nada que restaurar, y entonces `bom` seguía siendo el array de lo que acababa de entrar, así que cada línea se encontraba a sí misma y se sumaba su propia cantidad — comprobado revirtiendo el arreglo, un FortiGate 200G llegaba con cantidad 2 y $22.954. **(2) Cotizar un segundo equipo fundía su licencia dentro de la del primero**: la identidad de una línea se tomaba de `model + vendor`, y el `model` de una referencia es el nombre comercial del bundle — «Enterprise Protection» es el mismo texto en un 30G que en un 200G, así que la licencia de $1.147,50 se metía en la de $21.205,80. Ahora `identidadLinea()` decide eso en **un solo sitio** para los tres puntos que lo preguntan, y es el SKU para una referencia y fabricante+modelo para un equipo. `scripts/contrastes/cotizador-bom.js` conduce las dos pantallas y los caza: **no lleva ni una cifra del catálogo**, declara la *relación* —la cotización vale lo que ya llevaba más el BOM que entra, y el equipo aparece una sola vez— y lee los importes de la pantalla, para no ponerse rojo en cada cambio de precio. De paso es el primer caso que conduce `cotizador.js`, que estaba **sin conducir** y pasa al 65 %.
- **El BOM sigue al dimensionamiento, y la regla vive en un solo sitio.** `BOM.sincronizar()` en `js/bom.js`. Cada página tenía su propia copia de `llevarABom`, y **medido en el navegador el 2026-09-03 las copias no hacían lo mismo**: Fortinet, MikroTik y Aruba seguían al dimensionamiento; Cisco y Huawei se quedaban cotizando el equipo anterior; Juniper solo repintaba su BOM al abrir la pestaña. **La causa era una sola línea** — `llevarABom(id)` empezaba con `if(!id) return;`, así que cuando el dimensionamiento se quedaba **sin candidato** el BOM no se enteraba y seguía mostrando el último equipo que sí cumplía, en silencio: en Cisco a 20 Gbps se exportaba una cotización de un Catalyst 8200L de 1 Gbps para un requerimiento que ningún equipo cumple. Ahora se repinta **siempre**, también cuando el modelo no cambia, porque el aviso y las cantidades dependen de más cosas que el id. **Elegido a mano y heredado no son lo mismo**, la misma distinción que `ficha.js` hace con el equipo recomendado: el desplegable del BOM cotiza cualquier equipo a propósito, así que una elección manual no se pisa —se detecta por el evento `change`, que nunca dispara una asignación por código— pero una elección heredada sigue siempre al cálculo. Y `BOM.avisoDesvio()` declara los dos desajustes, que no son el mismo: «no hay candidato» y «estás cotizando otro equipo». Existía solo en la página de Fortinet; al vivir en el módulo lo dicen los siete fabricantes con las mismas palabras.
- **Una referencia se puede añadir a la cotización, no solo mirar.** `BOM.agregarRef/quitarRef/refsExtra` en `js/bom.js`, con el botón «Añadir» que `ficha.js` pinta en cada fila de referencias. Ver el bundle de FortiCare de un FortiGate no servía de nada si luego había que teclear esa línea a mano en el cotizador. **Viven en `bom.js` y no en cada página** porque `renderTabla` es el punto único por el que pasan los siete dimensionadores: gestionarlas ahí las da a los siete sin tocar ninguno. **Sobreviven al repintado, que es todo el punto**: el BOM se repinta en cada cambio de escenario, así que una referencia guardada en el array de filas de la página se habría borrado al mover el caudal —el mismo modo de fallo que ya tuvo `llevarABom`—; se guardan aparte y se vuelven a pegar en cada render. **Una sola clave para los siete, no una por página** (2026-09-09): la primera versión guardaba en `presales-bom-refs:<pathname>`, así que añadías un bundle de Fortinet, ibas a Aruba y al enviar al cotizador desde allí el de Fortinet se quedaba atrás — una pérdida silenciosa, justo en la pantalla que existe para armar una cotización **multi**-fabricante. Ahora el fabricante que cada referencia ya llevaba dentro es lo que las separa: el BOM de cada dimensionador muestra **solo las suyas** (`BOM.fijarVendor`, que `ficha.js` informa) pero `enviarACotizador` manda **todas**. La clave de una referencia es `fabricante|sku` y no el sku suelto, porque dos fabricantes pueden traer el mismo código y quitar uno habría quitado el otro. Y la clave vieja **se migra** en la primera lectura y luego se borra: quien ya tuviera referencias guardadas las habría visto desaparecer al desplegar, que es exactamente la pérdida de datos que este cambio venía a evitar. **La cantidad se edita en la propia fila** (`BOM.cantidadRef`), y solo en lo añadido a mano: las filas que calcula el dimensionador salen de su motor, y dejarlas editables invitaría a cambiar a mano una cifra que el próximo repintado pisa sin avisar. El campo escribe con `change` y **no** con `input`, porque guardar repinta la tabla entera y reaccionar a cada pulsación destruiría el campo a medio teclear —escribir «12» pasa por «1»—; una cantidad menor que 1 quita la línea, que es lo que significa escribir 0. Entran en el cálculo **antes** de los totales, porque un bundle que no suma da un total que no corresponde a lo que la cotización lleva dentro. **El equipo y la referencia viajan distinto al cotizador a propósito**: el equipo solo como nombre, porque su precio y su texto salen de `CATALOG`, que es la fuente de verdad de esa pantalla; una referencia no puede hacer eso porque no está en `CATALOG` (son 6.849 solo de Fortinet frente a sus 54 equipos), así que viaja con su SKU, su descripción, su precio **y su fabricante** — fijar el fabricante en el cotizador habría pintado de Fortinet una referencia de Aruba, un dato inventado de los que no fallan, solo mienten. El color sale de `CATALOG` buscando el fabricante real.
- **La capa comercial sube al módulo compartido, y lo que es del fabricante se declara.** `BOM.simuladorDescuento()` y `BOM.tco()` en `js/bom.js`, paso 1 del orden de `docs/portabilidad-aruba.md`. El **simulador de precio neto** no depende de ningún dato de fabricante —lee un tramo y un porcentaje— así que **el control se construye en el módulo**, con sus tramos y su aviso de «simulador genérico, no el descuento real del distribuidor»: añadirlo a otra pantalla es una línea, como `ESTADO.botonEnlace`, en vez de doce de marcado repetido en siete archivos que luego divergen. Conserva los ids `selDescuento`/`dtoCustom` porque `estado.js` ya los serializa, y por eso están declarados en `TARDIOS` de `catalogo-check.js`. El **TCO** se calcula ahora sobre las **filas del BOM**, que ya son la forma neutra; antes salía de los objetos de licenciamiento de Aruba (`capTier`, `licHa`, `boostBlk`, `tierPrice`) y eso era lo que lo ataba a una sola página. **Qué cuenta como OPEX lo declara la página** (`BOM.tco(filas, {opex, anios})`), por lo mismo que las reglas de agregación: que una suscripción sea recurrente y una licencia perpetua no lo sea es el modelo comercial de cada fabricante, no una propiedad de la fila — quien no declare nada tiene todo en CAPEX, que es lo correcto para un catálogo que solo vende hardware. **Se contrastó antes de cambiarlo**: siete escenarios medidos en el navegador —incluidos Boost y DTD, que son los que traen las categorías del camino largo— con las tres cifras idénticas a las del cálculo anterior. Lo que **no** subió es la matriz de accesorios: solo Aruba tiene compatibilidad declarada, y construir la pantalla antes que el dato produce seis paneles vacíos.
- **Los perfiles multi-sede son de todos los fabricantes, no de uno.** `BOM.perfiles/perfilesDe/guardarPerfil/quitarPerfil/consolidar` en `js/bom.js`. Un perfil guarda un escenario completo más **cuántas sedes idénticas** se cotizan con él, y nació en `arubaPerfilesV1` — una clave por fabricante. Pero un perfil multi-sede es *por definición* el caso de las 50 sucursales, y un despliegue real de 50 sedes **mezcla marcas**: spokes Fortinet contra un core Nokia. Con una clave por página el consolidado de cada fabricante ignoraba al resto en silencio, el mismo fallo que `presales-bom-refs:<pathname>`. Ahora hay **una sola clave** (`presales-perfiles`), cada perfil lleva su `vendor` dentro y la clave vieja se migra en la primera lectura. **Cargar es del fabricante; consolidar no**: `campos` son los ids del formulario de *esa* página —aplicar un perfil de Fortinet al de Aruba no significa nada— pero `filas` es la forma neutra que los siete comparten, así que el BOM global suma todos y agrupa por `fabricante|sku`, no por sku suelto. Se borra **por id y no por índice**, porque en una lista compartida el índice deja de ser estable. Y **las reglas de agregación las declara la página** (`BOM.consolidar(perfiles, {agregadas, unicas})`): el pool de Boost en una línea y el Orchestrator único por fabric son el modelo comercial de Aruba, y dejarlos a fuego en el módulo haría que cualquier fabricante que use esos nombres de categoría heredara su semántica de precios sin que nadie lo decidiera — el error del `noAplica` deducido. Quien no declare nada multiplica todo por sedes, y un consolidado que mezcla marcas **lo dice en pantalla**, no solo en el Excel.
- `js/bom.js` — the BOM table and its "Exportar a Excel" action, shared by the four dimensionadores. Each page just builds an array of `{ cat, desc, sku, qty, unit, nota }` rows; the module renders them, totals the priced lines and reports how many stayed unpriced instead of showing a total that looks complete. It carries its own CSS and reads the `:root` colour variables each page already declares, so every vendor keeps its accent for free.
- `dimensionador-juniper-srx.html` + `js/dimensionador-juniper-srx.js` — dimensionador Juniper, con dos plataformas separadas: **SRX** (cortafuegos, por capa de inspección) y **Session Smart Router** (SD-WAN sin túneles, una sola cifra). No se comparan entre sí a propósito, por lo mismo que Cisco acota la plataforma antes que el caudal.
- **Nokia tiene dos dimensionadores porque tiene dos preguntas.** `dimensionador-nokia-7220ixr.html` (2026-09-02) es el único del portal que **no elige un equipo**: diseña un **fabric de datacenter** (línea 7220 IXR, Clos de dos capas leaf-spine en malla completa). A partir de servidores, velocidad de acceso y sobresuscripción calcula leafs, uplinks por leaf y spines necesarios — por eso no reutiliza `js/ficha.js` (que asume "un equipo cumple un requerimiento"), aunque sí `js/bom.js` y `js/estado.js`. `dimensionador-nokia-7750sr.html` (2026-09-03) cubre los **otros 14** (7250 IXR, 7250 IXR-X, 7250 IXR-R, 7750 SR/SR-s/SR-1x): ahí sí hay un equipo elegido, así que usa `ficha.js` como los otros cinco. **La plataforma se elige antes que el caudal**, igual que en Cisco: un router de cell site, un agregador de datacenter y un PE de core IP/MPLS no son intercambiables aunque coincidan en Tbps. Dos reglas propias de esa página, y las dos salieron de estructurar texto libre: **las configuraciones de puertos son alternativas, no acumulables** («36x100GE o 12x400GE» nunca da 48 interfaces, así que el motor comprueba si *alguna* configuración cumple), y **un chasis modular no publica densidad** («7 slots IOM» dice cuántas tarjetas caben, no cuántos puertos salen), así que esos cinco se dimensionan por caudal y **se apartan con su motivo** en vez de descartarse en silencio o colarse con una densidad inventada. `legacyData/nokia.js` estructura en `MODELS` y `MODELS_ROUTER` los puertos y capacidades que ya estaban verificados como texto libre en `indexPR.js`, sin inventar ni corregir ningún dato — la capacidad va en Gbps aunque el material comercial la cite en Tbps, porque mezclar unidades haría que 6,4 Tbps perdiera contra 300 Gbps al ordenar.
- `guia-diseno-interactiva.html` + `js/guia-diseno-interactiva.js` — interactive topology reference. Fetches `/api/guia/roles` (was `EQ`); the SVG topology diagrams themselves (`TOPOS`/`nodes`/`links`) are still static, unchanged.
- `login.html` + `js/login.js` — the login form. This is the only page (and script) exempted from the auth wall; `js/login.js` has to stay public or the form would be inert.
- `cuenta.html` + `js/cuenta.js` — identidad (usuario y rol), cambio de la **propia** contraseña y cierre de sesión, sobre `/api/cuenta/*` y `/logout`. Avisa mientras siga en uso la contraseña semilla, y muestra el enlace a `/usuarios` solo si el servidor informa ese permiso.
- `usuarios.html` + `js/usuarios.js` — panel de administración: usuarios registrados (con una insignia «cambio pendiente» para quien todavía no completó su primer acceso), roles con sus permisos, y el formulario de alta. Crear un usuario devuelve su contraseña temporal **una sola vez**, en pantalla, con botón de copiar; el servidor no la guarda ni la registra en ningún log.

## Manual de usuario

`docs/manual-usuario/` — el manual para quien usa la herramienta, no para quien la mantiene: el recorrido de los seis dimensionadores, la selección de equipo a fondo (el desplegable, las insignias, «Volver al recomendado»), la pestaña de BOM, compartir un escenario y el cotizador. `manual.html` es la fuente, con la misma paleta y tipografías de la propia aplicación; `npm run manual` (`scripts/generar-manual-usuario.js`) lo imprime a PDF con Chromium sin cabeza. Las tipografías están vendidas en `fonts/` en vez de traerse de Google Fonts en cada corrida: el Chromium de este entorno no confía en el certificado del proxy de salida aunque `curl` sí, así que la generación no depende de la red. Playwright queda **fuera** de `package.json` a propósito — es una dependencia pesada para una tarea que se corre pocas veces al año; el script la busca donde ya vive en el entorno de trabajo habitual y dice exactamente qué instalar si no la encuentra.

## Conventions

- **No inline JavaScript.** The CSP is `script-src 'self'`, so an inline `<script>` block or an `onclick=` attribute simply won't run: put behaviour in `public/js/` and wire handlers through the existing click delegation. Inline `style=` attributes are fine — `style-src` deliberately keeps `'unsafe-inline'`.
- **Juniper: la cifra de portada no dimensiona, y no se sustituye por la de otra capa.** Juniper publica el firewall de la línea SRX en dos bases —**paquetes grandes** (`fw`, la del material comercial) e **IMIX** (`fwImix`, parecida al tráfico real)— más `ips` y `atp` (Threat Prevention) por separado. En el SRX345 son 5 Gbps, 1,7 y 0,6: un salto de un orden de magnitud entre la cifra que se cita y la que aguanta el equipo con inspección activa, el mismo error que la auditoría de FortiGate documentó. `CAPAS` en `dimensionador-juniper-srx.js` deja `fw` **fuera** de la escala de inspección: se muestra como referencia y nunca se elige con ella. Y un modelo sin cifra en la capa efectiva se **descarta explicando por qué**, en vez de rellenarse con la de otra capa — que es justo lo que produce propuestas cortas por un orden de magnitud. **Para completar lo que falta hay `npm run juniper`** (`scripts/importar-juniper.js`), el equivalente Juniper de `npm run cps`: acepta CSV/TSV/XLSX, reconoce las columnas por su cabecera, resuelve Gbps frente a Mbps por contraste en vez de multiplicar a ojo, y **solo acepta una fila si al menos dos de sus columnas casan con lo ya verificado y ninguna lo contradice** — el doble anclaje es lo que caza la fila desplazada, porque una cifra sola siempre parece plausible y el resto de su fila no. 2026-09-02: la matriz oficial se trajo vía GitHub Actions (mismo patrón que `cps` de Fortinet) y confirmó que ese doble anclaje funciona en ambos sentidos — corrigió `fwImix` de la línea SRX300 y `vpn`/`sess` del SRX1500, que una reconstrucción previa por búsqueda había adivinado mal, y completó `atp`/`sess`/`cps` donde faltaban (ver `legacyData/juniper.js` para el detalle). El SRX380 quedó **a propósito** sin corregir en `fw`/`fwImix`/`vpn`, aunque el documento trae una fila que los contradice: de esos campos solo `ips` coincide con lo ya guardado, un único anclaje por debajo del mínimo — corregirlo exige `--sin-contraste` bajo responsabilidad de quien decide. Los modelos que hoy solo traen `fw` (SRX4300, SRX4700, SRX4100, SRX4200, de una generación que ese documento de 2020 no cubre) tampoco alcanzan ese anclaje y se apartan salvo que se pase `--sin-contraste`.
- **Cisco: la plataforma se elige antes que el caudal.** El catálogo mezcla cinco líneas que no son intercambiables aunque coincidan en Mbps — IOS XE SD-WAN (Catalyst 8000 y Secure Router G2), ISR 1000, Meraki MX y ASR 1000 — porque cambian el plano de gestión, el licenciamiento y quién opera la red. `PLATAFORMAS` en `dimensionador-cisco-catalyst8k.js` acota primero por familia (`ser`) y dentro de ella sí aplica el más pequeño que cumple, como los otros cuatro dimensionadores. Antes no hacía ninguna de las dos cosas: tomaba el primero del catálogo que cumpliera, y el catálogo está ordenado por familia, así que para 3 Gbps proponía el chasis 8500-12X4QC de 31,9 Gbps. Ordenar por capacidad sin acotar la plataforma es peor: hace saltar de un Catalyst a un Meraki por unos Mbps. En perfil SD-WAN, un modelo sin cifra propia cae a la de IPsec y **la lista lo marca** («cifra IPsec»), porque son dos mediciones distintas y sin la marca un equipo sin dato publicado adelanta a uno que sí lo tiene. El **C8355-G2 ya no es uno de ellos**: la ficha oficial de la serie 8300 sí publica su SD-WAN y son **8,7 Gbps** (2026-09-03), frente a los 20 Gbps de IPsec con los que se dimensionaba antes — 2,3 veces por encima, en el único perfil en el que ese equipo se vende. La misma ficha corrigió su `redund` a `true` (trae entrada de alimentación doble con dos fuentes por defecto) y le dio 45 W de consumo típico.
- **Los filtros del cotizador salen del catálogo, no de una lista escrita a mano.** La lista fija se quedó en seis fabricantes y dejó a Aruba y MikroTik en el listado agrupado pero sin botón de filtro — visibles entre 139 equipos, imposibles de acotar. `VENDORS` se deriva ahora de `CATALOG`.
- **Fortinet: las funciones de inspección fijan un piso de capa, nunca un recargo porcentual.** Las cinco cifras del Product Matrix miden rutas de procesamiento distintas, así que activar antivirus no encarece un 8 % la cifra de firewall: hace que aplique la de Threat Protection, que en gama de sucursal es un orden de magnitud menor. `PISO_POR_FUNCION` en `dimensionador-fortinet-fortigate.js` mapea cada función a su capa mínima y `capaEfectiva()` toma la más profunda entre esa y la que eligió el usuario. El motor anterior sumaba porcentajes al requerimiento sin tocar la capa, lo que declaraba 93 % de holgura sobre un FortiGate 60F que iba al 100 % — factor 14,3x. FortiSandbox no aparece en el mapa a propósito: analiza fuera de banda y no consume throughput del equipo. **El derate de SSL se retiró el 2026-09-22**: la inspección TLS es un eje propio con la cifra oficial del Product Matrix (ver la entrada del informe de validación técnica más arriba).
- **Fortinet: el overlay SD-WAN es un segundo techo, no un adorno.** Cuando el rol es spoke o hub, la fracción del tráfico que va cifrada atraviesa además el motor IPsec, así que la capacidad efectiva es `min(capa de inspección, IPsec / fracción del overlay)` — con breakout local parcial el techo de IPsec se reparte entre menos tráfico y deja de ser el limitante. El control anterior (un enlace / dual WAN) no entraba en ningún cálculo. El modo agregado (sedes x caudal x simultaneidad) es el del concentrador y el rol `hub` lo activa solo, porque dimensionar un hub en modo enlace único es exactamente como se queda corto. `OVERHEAD_ESP` (6 %) y el factor de simultaneidad son supuestos de la herramienta, no cifras publicadas, y se declaran donde se usan. El límite de túneles por modelo **no está en el catálogo**: se muestra cuántos hacen falta y se avisa de confirmarlo en el datasheet, en vez de inventarlo.
- **Fortinet: las sesiones concurrentes se derivan de los usuarios, y casi nunca son el eje que limita.** El campo pedía un total absoluto que nadie sabe estimar; ahora es `usuarios x sesiones por usuario` (20 típico corporativo), con el total como anulación para CGNAT y portales. El hallazgo que justifica el diseño: con las densidades de este catálogo —577 a 2.121 sesiones concurrentes por Mbps de Threat Protection— la tabla de sesiones no limita antes que el throughput en ningún perfil humano; a 3 Mbps por usuario harían falta entre 1.700 y 5.500 sesiones **por usuario** para empatar. Solo compite cuando el caudal por dispositivo es muy bajo y las sesiones muchas (IoT, CGNAT). La página muestra qué eje manda y a cuántas veces está el otro, para que nadie suba de gama por un límite que está a dos órdenes de magnitud. El eje que sí aprieta —**sesiones nuevas por segundo**— ya está modelado: ver la convención siguiente.
- **Fortinet: las sesiones nuevas por segundo son un tercer eje, y se derivan de la vida media de la sesión.** `cps` (New Sessions/Sec del Product Matrix) mide CPU; `sess` mide memoria. No se pide como dato suelto: si un usuario sostiene N sesiones y cada una vive V segundos, abre N/V por segundo, así que `cpsNeed = sessNeed / vidaSes` con 30 s por defecto — supuesto de la herramienta, declarado en la página. `ejesDe()` en `dimensionador-fortinet-fortigate.js` es el único lugar que decide qué eje manda, para que la ficha, el resumen y la exportación no se contradigan; un eje sin dato no entra en esa comparación. **`cps` está en 56 de los 58 modelos y en `null` en los otros 2** (100F y 200F). **Y `ssl` está en 51 de los 58** desde el 2026-09-23, leído del Product Matrix de septiembre que ya estaba en la rama de transporte (doble anclaje 27/27 contra `sess` y `cps`). Los 7 que faltan son los que esa edición ya no lista —es un *Top Selling Models Matrix*— y se apartan con su motivo. Con ellos entraron `tunGw`, `tunCli`, `sslVpnUsers`, `sslVpn`, `policies` y `vdomMax`, que convierten en comprobación lo que la pantalla solo podía declarar. `npm run catalogo` lo cuenta. Los cinco que faltaban no estaban en el Product Matrix —es un "Top Selling Models Matrix", un subconjunto curado—, pero sí en las fichas por serie: las de 400F y 600F se bajaron el 2026-09-03 con `traer-fortinet-datasheets.yml` y dieron 400F/401F 500.000 y 600F 550.000, con su Concurrent Sessions casando con el `sess` ya verificado. Las de 100F y 200F no están en la URL que sigue el patrón del resto (404 reportado, no dado por bueno), y `null` significa "el catálogo no trae el dato", no "no tiene límite": esos modelos no se filtran por ese eje y la ficha lo declara sin comprobar. La cabecera de `legacyData/fortinet.js` documenta la procedencia completa: los 21 originales por búsqueda web con doble filtro, y 32 más (2026-09-02) leyendo el PDF real página por página tras traerlo con `.github/workflows/traer-fortinet-matrix.yml` — los ejecutores de GitHub Actions sí llegan a fortinet.com aunque este entorno no, así que el workflow lo publica en una rama de transporte (`fuente/fortinet-product-matrix`, nunca `main` ni un PR: no es un activo de la aplicación) que se trae con `git fetch` y se descarta tras transcribir. **Para completarlos hay `npm run cps`** (`scripts/importar-cps.js`), el equivalente Fortinet de `npm run datasheets`: se corre desde una máquina con acceso al Product Matrix, acepta CSV/TSV/XLSX de dos columnas, normaliza el nombre del modelo (`FG-90G` = `FortiGate 90G` = `90G`), propaga a las variantes con SSD deduciendo el parentesco del propio catálogo, y si el archivo trae además la columna de Concurrent Sessions **rechaza la fila cuando no coincide con el `sess` verificado** — que es lo que detecta una fila desplazada, porque la cifra sola siempre parece plausible; los 32 nuevos pasaron ese contraste sin un solo rechazo. No lee el PDF directamente a propósito: extraer una tabla de un PDF es justo donde se cuelan esos desplazamientos — de ahí que incluso con el PDF ya disponible, la transcripción a CSV siga siendo manual, página por página, y solo el contraste final sea automático. Donde el documento publica un segundo valor con licencia Hyperscale (nota⁶), se transcribió siempre el valor base, igual que ya hace `sess`. **RAM por modelo no existe en el Product Matrix** — ese documento publica throughput por capa, sesiones, cps, interfaces y **fuentes de alimentación**; el proxy de la capacidad de memoria es `sess`. *Corregido el 2026-09-14 leyendo la edición de septiembre: esta línea decía «y consumo», y no es cierto — el Matrix publica «Power Supplies» (tipo y número, que es lo que respalda `redund`), no vatios. Los vatios salen de la tabla «Dimensions and Power» de cada ficha por serie, como ya decía la sección de alimentación.*
- **Huawei: el portafolio comercial no dimensiona, y por eso `fwd` y `typ` son campos distintos.** `e.huawei.com` publica la cifra de paquetes grandes: en el AR5710-S son 1300 Mbps frente a los 620 típicos, un factor 2,1 — el mismo modo de fallo que en el SRX380 vale un factor 10 y en el FortiGate 60F valió 14,3x. **`npm run huawei`** (`scripts/importar-huawei.js`) es el tercero de la familia de importadores, con el mismo contrato que `cps` y `juniper`: `--check` inventaría los huecos sin salir a la red, reconoce las columnas por su cabecera, resuelve Gbps frente a Mbps por contraste en vez de multiplicar a ojo, y **solo acepta una fila si al menos dos de sus columnas casan con lo ya verificado y ninguna lo contradice**. Añade un modo `--eol` que carga los boletines de fin de venta como `eolAnnounced` con su fecha real —no como una marca fija—, para que la regla de `ficha.js` degrade el equipo sola el día que vence su último pedido. **Y `--plantilla` escribe `huawei-specs.csv` y `huawei-eox.csv` ya con los modelos y las cabeceras que el propio importador reconoce**, para que quien tenga acceso a Info-Finder solo pegue cifras en vez de construir la hoja — las celdas ya verificadas van rellenas a propósito, porque son las que el doble anclaje usa para cazar una fila desplazada. Se genera y **no** vive commiteada: una plantilla guardada se queda con los modelos de ayer, y en un catálogo que cambia eso es pedir datos de equipos que ya no están y no pedir los de los que entraron. Cobertura actual: los 23 AR sin `mpps`, las 17 NetEngine sin `fwd`/`ipsec`/`typ`, y **0 de 40 modelos con ciclo de vida**, que es el hueco más caro del catálogo.
- **Aruba: la lista del distribuidor entra por un importador gobernado, y la lista misma nunca entra al repositorio.** `npm run lista-aruba` (`scripts/importar-lista-aruba.js`) es el cuarto de la familia de importadores, pero su riesgo es distinto al de `cps`/`juniper`/`huawei`: allí el peligro es la fila desplazada y el ancla son dos columnas que casen; aquí el peligro es **filtrar material confidencial de canal**. Por eso extrae *únicamente* cinco columnas permitidas —SKU, descripción, List Price, vigencia y PLC— con validación literal de la cabecera, y **nunca** el nombre del distribuidor, el PA Number, el Net Price ni el PA Discount. Va en *dry-run* por defecto: sin `--aplicar` no escribe nada, y lo que escribe es solo el CSV del cotizador (`public/datasheets/aruba-lista-precios-hpe.csv`), que es el que sí vive en git. Sus pruebas usan **fixtures sintéticos** por la misma razón. Reporta el diff en cinco canales (repo≠lista, CSV≠lista, PLC, ausentes, candidatos nuevos), y un SKU que la lista marca `ES` no se oferta.
- **Disclose unverified data, never invent it.** Fortinet's catalog is verified against a signed price list; MikroTik's is not, and its `legacyData/` header says so. Where a SKU or list price isn't confirmed, the field stays `null` and the BOM renders the line as "sin cotizar" (`bom.js` counts them and warns). Aruba is a middle case since 2026-09-10: 15 EdgeConnect/gateway models with a confirmed SKU have HPE List Price (extracted from an authorized distributor's price export — see `DATASHEETS.priceList` in `aruba.js` and `public/datasheets/aruba-lista-precios-hpe.csv`), but it's list price without the distributor's negotiated discount, not a signed price list like Fortinet's — everything else in the Aruba catalog (subscriptions, support, models without a confirmed SKU) is still `null`. A plausible-looking invented SKU is the failure mode this catalog already had once (see the `FortiGate 2000F` note in `fortinet.js`), and `aruba.js` records its own instance of it: the first revision of that file carried an "EC-2XL" that does not exist, plus wrong licence-tier and support-offering names. Its header lists those corrections deliberately, so the next person can see what was wrong and why.
- Aruba models carry `legacy: true` on the AOS 8 controller lines (7000/7200). The sizing engine sorts current-generation gear ahead of it, so a legacy box is only recommended when nothing current fits — without that, the smallest-that-fits rule recommended a 7005 for a 1.5 Gbps branch, which is the wrong answer for a new deployment. The legacy line stays in the catalog on purpose: it is what an install-base expansion is quoted against.
- Aruba's `skus` array is the model for "orderable references": a list of `{sku, d}` rather than a prose field, so every part number is searchable, renderable and quotable. `hwSku` remains the headline SKU for the BOM line. Where HPE publishes no figure (the 9100's firewall throughput) or no official document URL (the 7200 spec sheet), the field is `null` and the UI says so rather than substituting a third-party copy.
- Licensing is not shaped the same for every vendor and the projections reflect that: Fortinet's SKUs embed the appliance model, so `LICENSES` is keyed by model; Aruba's subscription is priced by site bandwidth, so its `LICENSES` is keyed by bandwidth tier and Boost is a fabric-wide pool that appears once in the BOM regardless of unit count.
- Price fields use `elp` (display string) paired with `elpN` (numeric) — prices exclude channel discounts, taxes, and licensing/support costs.
- **Fuera de venta se muestra, pero no se recomienda — y la regla vive en un solo sitio.** `eol: true` on a `Product` hides it from `cotizador.html`/`index.html`; inside a dimensionador it stays visible, because ampliar un parque instalado es justo cuando hace falta consultarlo. Lo que no puede es salir recomendado. `FICHA.rango()` en `public/js/ficha.js` es la única implementación: **0** vigente, **1** línea anterior (`legacy` — se propone solo si nada vigente cumple), **2** fuera de venta (`eol`, o `eolAnnounced` con la fecha de último pedido ya pasada) — nunca se propone. Las cinco páginas ordenan con `FICHA.ordenar(lista, desempate)` y eligen con `FICHA.recomendar(lista, preferir)`; ninguna vuelve a decidirlo por su cuenta. Antes había tres criterios distintos: Fortinet y MikroTik **borraban** los descontinuados de la lista (ni recomendados ni consultables), Cisco los dejaba competir de igual a igual y podía proponerlos para un diseño nuevo, y Aruba tenía el suyo propio para `legacy`.
- **Un fin de venta anunciado no es lo mismo que estar fuera de venta.** `eolAnnounced: {pid, lastOrder, sucesor, url}` describe el boletín; hasta `lastOrder` el equipo se pide con normalidad, así que se marca pero sigue siendo recomendable, y **pasada esa fecha cae solo a rango 2** sin que nadie tenga que editar el catálogo — que es como estos avisos se quedan obsoletos. En Cisco están registrados los 4 chasis Catalyst 8300/8200, el 8500-12X4QC y los tres ASR 1000 (1001-X, 1002-HX y 1006-X), cuyas fechas de último pedido ya pasaron: hasta agosto de 2026 toda la línea ASR se ofrecía como si estuviera vigente.
- **Un conjunto de fuera de venta que no marca nada avisa.** `CISCO_EOL_MODELS` vivió meses en `seedCatalog.js` listando la serie ISR 4000 que la Fase 2 ya había retirado: no marcaba nada y nadie se enteró, porque un conjunto inerte se comporta igual que uno que funciona. Se borró, y `seedDimensionadorModels` ahora avisa por consola cuando una entrada de `eolModels` no casa con ningún modelo, para que `FORTINET_EOL_MODELS` no se pudra igual. La justificación que lo mantenía vivo («volvería a aplicar si reaparecieran por `cotizadorCatalog`») era además falsa: esa ruta crea sus filas en `backfillPricesFromCotizador`, que no consulta estos conjuntos.
- **Alimentación eléctrica: cinco estados, no dos.** `m.redund` (¿es de doble fuente?) es el campo que Cisco ya traía al 100 % de su catálogo (`redund: true|false`); se extendió a los otros cinco fabricantes, pero **solo donde el propio catálogo ya lo dice** — nunca se dedujo del tamaño o la gama del equipo. `undefined`/`null` significa «el catálogo no lo dice», y `FICHA.seccionAlimentacion(m)` en `ficha.js` lo declara así explícitamente («el catálogo no lo especifica») en vez de leerlo como `false`, que sería inventar un dato negativo. **El cuarto estado, `'opcional'`, salió de leer los datasheets de FortiGate el 2026-09-03**: el 80F y el 90G publican «Powered by up to 2 External DC Power Adapters (1 adapter included)» — salen de fábrica con una sola fuente pero admiten la segunda, así que `true` habría prometido algo que no viene en la caja y `false` habría negado una redundancia que el equipo sí soporta. **Y el quinto, `'no-aplica'`, llegó con MikroTik y Aruba**: las licencias CHR y el EdgeConnect virtual son software sobre un hipervisor, no tienen fuente ninguna, y dejarlos en «el catálogo no lo especifica» haría esperar un dato que no existe — el mismo cuidado que el resto de este catálogo tiene con los precios de Aruba o el `cps` de Fortinet. `m.psu` es opcional y añade lo que haya de consumo (`watts`), tipo (`AC`/`DC`) o rango de entrada (`volts`/`amps`), siempre transcrito de una frase ya publicada en el propio `legacyData` (`fuentes 1+1 · N W típicos`, `doble fuente 350 W`, `PSU y almacenamiento redundantes`…), nunca inferido. Cobertura real: **Cisco 21/21** (ya existía), **Huawei 17/40** (la serie NE8000 y el AR8140, con vatios; el resto de los AR no menciona fuente), **MikroTik 14/15** y **Aruba 10/25** (2026-09-03: fichas de producto de mikrotik.com y el *EdgeConnect Hardware Reference*, ambas traídas vía Actions; ampliado el 2026-09-10 con los QuickSpecs oficiales de EC-10104/10106/10108/10150, leídos vía Jina Reader — ver *Cerrado recientemente*. Dos matices que obligaron a mirar más allá del sí/no: varias entradas de alimentación **no** son doble fuente —el RB5009 tiene tres entradas sobre una sola fuente interna— y ni MikroTik ni HPE publican un consumo *típico*, sino máximos y requerimientos, así que esas cifras van en el texto y no en `psu.watts`, que la ficha rotula «Consumo típico»), **Juniper 12/12 SRX** (2026-09-03: las *hardware guides* de juniper.net, una por modelo — el material comercial publica rendimiento, no alimentación. **Cinco de ellos son `'opcional'`**: Juniper es explícito en que envía el SRX1500, SRX1600, SRX2300, SRX345 y SRX4300 con una sola fuente y vende la segunda aparte. El SRX340 y el SRX345 son la mejor prueba de por qué esto se lee modelo por modelo: consecutivos en la misma serie y opuestos — el 345 admite la segunda fuente, el 340 lleva la suya fija en el chasis y no reemplazable en campo. Y el **SRX320 se queda sin `watts` aunque su guía sí publique consumo medio**, porque publica dos —46 W sin PoE y 221 W con PoE, factor 4,8— para una sola entrada de catálogo: elegir una sería correcto para la mitad de los pedidos y falso para la otra mitad, así que las dos van en el texto) **Nokia 6/18** (2026-09-03: los cuatro 7220 IXR-D y los dos 7750 SR-1x, de sus fichas de serie, todos «1+1 redundant» literal. Hasta esa fecha Nokia ni siquiera figuraba en esta lista ni en `npm run catalogo` — el registro contaba seis fabricantes de siete, así que el hueco no se veía. Ninguno lleva `watts`: los vatios que publica el 7220 IXR-D son de la fuente y no del equipo, y lo prueba el propio documento — el D2L y el D3L declaran los mismos 650 W con capacidades distintas) y **Fortinet 56/58** (2026-09-03: 26 fichas por serie más los System Guide de los chasis, traídas vía Actions y leídas a mano — el Product Matrix no publica esta cifra, pero la tabla «Dimensions and Power» de cada ficha por serie sí. Fortinet sirve las fichas nuevas en `/data-sheets/pdf/` y las de la generación F en `/data-sheets/`, un subdirectorio de diferencia que explicó doce 404. Solo quedan el 200F, cuya ficha da 404 en ambas rutas, y el 70F, porque `fortigate-70f-series.pdf` resultó ser la ficha del **71F** — el 70F no aparece ni una vez en ella, y aplicarle esas cifras habría sido creerle al nombre del archivo en vez de a su contenido). La sección aparece en las seis páginas por igual, incluso donde todo sale `null`: la pregunta merece hacerse aunque hoy no tenga respuesta.
- **Renombrar una página pública exige redirigir la anterior.** El dimensionador Huawei se llamaba `dimensionador-bom-huawei-v3_1.html` (versionado informal previo a git) y hoy es `dimensionador-huawei-netengine.html`; `RENOMBRADAS` en `server.js` redirige la ruta vieja **conservando el querystring**, que es donde viaja el escenario compartido — sin eso el enlace llegaría a la página correcta con los parámetros por defecto, que es peor que un 404 porque no se nota. La clave de `localStorage` conserva a propósito el nombre viejo: es la identidad bajo la que la gente ya tiene escenarios guardados, no el nombre del archivo.

## Roadmap (see plan history for full detail)

Phase 1 (this migration) transcribed the existing hardcoded data as-is for structural parity. 
Phase 2 replaces it with data verified against official Huawei/Cisco/Fortinet sources (e.g. removing EOL ISR 4000 series and replacing with Catalyst 8000). 
Phase 3 added a real "Sincronizar" button (IA Sync) powered by Anthropic's Claude API (`claude-opus-5`). It supports file uploads (PDF datasheets, Excel/CSV matrices, plain text) to perform strict, zero-duplication comparisons against the active database and propose structured updates. **Replanteado el 2026-09-08 para que también sincronice en producción sin escribir la base efímera**: analizar corre en cualquier entorno, y el cambio se hace durable descargando la propuesta y aplicándola sobre `legacyData/` con `aplicar-propuesta.yml`, que abre un PR con anclaje (el token de escritura vive en Actions, no en el servicio). Documentación oficial del módulo en `docs/sincronizacion.md`.
Phase 4 closed the site off and hardened it: shared-credential login with a signed session cookie, layered brute-force limiting, all page JavaScript moved out to `public/js/` so a strict CSP could be turned on, and `cors()` removed.
Phase 5 added the MikroTik dimensionador and the shared `js/bom.js` BOM table with Excel export.
Phase 6 added HPE Aruba Networking: EdgeConnect SD-WAN (with the Boost acceleration add-on) and the SD-Branch 9000-series gateways, wired through every layer — catalog, portal page, cotizador, design-guide roles and its own dimensionador — with its data provenance explicitly marked unverified.
Phase 6b replaced that first-pass Aruba data with figures and SKUs taken from HPE's own product and store pages, added the 9200-series campus gateway, the portfolio software (Orchestrator, Central, ClearPass) and Foundational Care support, and linked each model to its official datasheet (`DATASHEETS` in `aruba.js`, surfaced on the page). Prices for most lines remain unverified; 2026-09-10 added real HPE List Price for the 15 EdgeConnect/gateway models with a confirmed SKU (see the note above) — still not a signed price list like Fortinet's.
Phase 6c fixed the catalog's *coverage* rather than its accuracy: it went from 9 models to 21 by adding the families a keyword-driven search had missed — the 9100 Hybrid Gateways (wrongly deleted in 6b), the 9004-LTE, and the AOS 8 controller lines (7000 branch, 7200 campus) — and turned the orderable references into structured `skus` data instead of prose buried in a `variantes` string, which had been hiding roughly twice as many real part numbers as the catalog displayed.
Phase 7 turned the recommendation into a choice: every dimensionador lists all qualifying models in a dropdown (`js/ficha.js`) with the full sheet — specs, proposed licensing, software and support — for whichever is selected, and the portal's per-vendor catalogs were unified under the Fortinet "Throughput de referencia" treatment (columns still differ per vendor, because not every maker publishes per-inspection-layer figures).

Phase 8 (September 2026, largely delivered by a separate AI engine working directly on `main`) made the dimensionador the landing page of each of the seven vendors instead of a section inside the portal, gave Aruba real HPE List Prices from an authorized distributor's export plus a ~134-SKU accessory catalogue cross-checked against HPE's own compatibility documents, and rebuilt the Aruba dimensionador around the Multi-Underlay Builder (see the Aruba entry above), a 70/30 local-breakout model, licence tiers from 20 Mbps to 2 Gbps, and CAPEX/OPEX/TCO with multi-site profiles. Where that work's brief contradicted the vendor's own documents, **the document won and the discrepancy was written down** rather than quietly reconciled — see points 18, 19 and 28-32 of `PENDIENTES.md`, and `docs/refactor-aruba-2026-09-13/` for the contract it was built against.

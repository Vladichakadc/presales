## Cerrado

**El recordatorio.** `CLAUDE.md` manda consultar al asesor «cuando el mismo error aparece dos veces», y ningún ajuste lo forzaba.
- `.claude/hooks/lib-fallos.js` cuenta cuántas corridas seguidas de una misma acción de npm acabaron mal, desde la más reciente hacia atrás. Una corrida acaba mal si:
  - en `runs.jsonl` tiene `rc` distinto de 0, que es como el arranque salda lo que quedó abierto;
  - o sigue abierta en `en-curso.jsonl`, porque `PostToolUse` no se dispara cuando el comando falla.
- `.claude/hooks/aprendizaje.sh`, en `PreToolUse` y antes de abrir la corrida, con dos o más fallos devuelve el recordatorio en `additionalContext`. La sesión lo lee junto al resultado. `PreToolUse` admite ese campo según code.claude.com/docs/en/hooks.
- **Nunca lleva `permissionDecision`**: avisa, no aprueba ni frena. Un fallo esperado (una prueba en rojo a propósito) también cuenta, y el texto lo dice.

**Pruebas** (`test/aprendizaje-hook.test.js`). Conducen el hook con el JSON que manda Claude Code y comprueban cuatro cosas:
- el registro: `PreToolUse` abre y `PostToolUse` cierra con rc=0 (no tenía prueba);
- un comando que solo se menciona no se registra;
- dos fallos seguidos dan el recordatorio, sin `permissionDecision`;
- un solo fallo, un verde en medio o los fallos de otra acción no dan nada.

Caen los dos sabotajes: si la regla deja de contar, o si el hook devuelve `permissionDecision`.

**Comprobado en una sesión real.** Dos `npm run reservar -- --comprobar` fallidos a propósito. Al tercer intento llegó a la sesión «Las 2 ultimas corridas de "npm run reservar" acabaron mal…», y el comando corrió igual.

**Verificación:** `npm run verificar`, 1.421/1.421 y lint sin errores (los 9 avisos ya estaban). No toca `public/` ni `server/`.

## Estado

**Lo que no ve.** El código de salida de una línea de shell es el de su último programa. Si a npm le sigue una tubería (`| tail`) o un `;` (`> log; echo rc=$?`), un fallo de npm se registra con rc=0. Se midió con dos `reservar` en tubería que fallaron. Está escrito en `lib-fallos.js` y en `CLAUDE.md`.

**Mejora propuesta: que el registro no apunte un verde que no vio.**
- **Qué hace:** con npm seguido de `|`, `;` o `||`, el registro guarda `rc: null` («no se sabe») en vez de 0. Solo `&&` conserva el fallo de npm.
- **Qué evita:** dos errores que hoy pasan sin ruido.
  - El sello de `pre-push.sh` da por pasado un `npm run verificar > log; echo rc=$?` en rojo. Es la forma habitual de correrlo, así que el aviso antes de empujar no avisa justo cuando debería.
  - Este recordatorio se pierde los fallos en tubería.
- **Qué cuesta:** una función en `lib-comando.js` con su prueba, y que `pre-push.sh` ignore el `null`.
- **Qué se rompe si se hace mal:** `pre-push.sh` pediría confirmación en cada push de quien corre `verificar` con tubería, hasta que cambie de costumbre. Un sello que pregunta de más es mejor que uno que afirma sin haber visto, pero el dueño decide si ese ruido compensa.

**Criterio que conviene conservar:** un registro de corridas solo es fiable si sabe qué no vio. Un código de salida que no es el del comando se apunta como desconocido, nunca como éxito.
